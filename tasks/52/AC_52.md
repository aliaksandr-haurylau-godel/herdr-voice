# AC_52 — failures say what actually failed

Closes #52 and #78. Input: the two GitHub issues; neither has comments.

## As-is

Three places collapse every failure into one variant whose message names one
cause, whatever the real cause was.

**`src/rewrite/http.rs` (#52).**
- `HttpEngine::rewrite` maps both `ureq::Error::Status(code, _)` and
  `ureq::Error::Transport(t)` to `HttpError::Failed` (`src/rewrite/http.rs:163-172`).
  The response carried by `Status` is discarded, so the server's own explanation
  never reaches the person.
- `HttpError::Failed` prints one sentence for both: `cannot reach {url:?}: {detail};
  check the server is running and the address is correct` (`src/rewrite/http.rs:127-130`).
  A timeout and a 400 therefore both tell the person to check a server and an
  address that are fine. The issue records a 30-second timeout while the endpoint
  loaded a model, and a 400, both printed this way.
- The bound is `TIMEOUT`, 30 seconds (`src/rewrite/http.rs:90`). ureq reports a
  timeout as `Transport` of kind `Io` with the message `timed out reading response`
  (ureq 2.12.1, `src/stream.rs:98`); nothing in the current code looks at the kind.
- Existing tests: a 500 is asserted to be `HttpError::Failed` and to contain the
  URL (`src/rewrite/http.rs:351-361`); a refused connection is asserted to contain
  the address (`src/rewrite/http.rs:379-389`). No test produces a timeout or
  checks that a server's body is kept.

**`src/stt/http.rs` (named by no issue).**
- Same shape and same sentence. `HttpError::Refused` is used for every
  `Transport` error and prints the same "cannot reach … check the server is
  running and the address is correct" (`src/stt/http.rs:68-72`, `:155-158`).
- `HttpError::Failed` carries the status, but its `detail` is the fixed text
  `server answered with status {code}`; the response is discarded
  (`src/stt/http.rs:149-154`).
- A failure to read the take's own audio file is also reported through
  `HttpError::Refused`, so it prints "cannot reach {url}: could not read {path}:
  …; check the server is running" (`src/stt/http.rs:132-137`).
- The same 30-second `TIMEOUT` (`src/stt/http.rs:17`).

**`src/delivery.rs` (#78).**
- `HerdrDeliverer::run` maps every `Err` from `Command::output()` to
  `DeliveryError::NotFound { binary, path }` (`src/delivery.rs:186-189`), which
  prints "cannot run {binary:?}: it is not on the PATH this process has, which is
  {path:?}. Set HERDR_BIN_PATH … or start herdr from a shell where it is on the
  PATH" (`src/delivery.rs:19-24`). The operating system's reason is discarded, so
  a binary without the execute bit, a file still open for writing, or resource
  exhaustion all produce the `PATH` sentence.
- Existing tests cover the success path through a recorder script
  (`src/delivery.rs:477-520`). None starts a missing or non-executable program.
- `DeliveryError::NotFound { binary, path }` is also constructed by one daemon
  test (`src/daemon.rs:2619`).

## To-be

- Each distinct cause produces its own message, and each message says what to do
  about that cause.
- Where a server answered with a non-2xx status, the server's own explanation is
  part of the message, bounded in length.
- The "check the server is running and the address is correct" advice appears
  only where the cause is that the server could not be reached.
- The "not on the PATH" advice appears only where the program was not found.

## Requirements

Asked for by #52:
- R1. A timeout says the reply exceeded the bound, names the bound, and says what
  to do about it.
- R2. A non-2xx response says the server answered and refused, names the status,
  and includes what the server said.
- R3. Both are covered by tests against a local test double with no live
  endpoint: one that never answers, one that answers 400 with a body.

Asked for by #78:
- R4. A failure to start `herdr` reports the reason the operating system gave.
- R5. The advice matches the reason: the `PATH` sentence for a binary that is
  not found; something else for a binary that is found and cannot be run.
- R6. Covered by tests that produce at least the not-found and the
  not-executable cases; a fixture without the execute bit is enough for the
  second.

Carried by the run assignment, not by either issue:
- R7. `src/stt/http.rs` gets the same treatment as R1 and R2, because it prints
  the same sentence for the same causes.
- R8. The server's explanation is kept on a non-2xx status and is bounded in
  length.
- R9. Tests cover at least: timeout, connection refused, a 4xx with a body, a
  binary that is not found, a binary that is not executable.

Implied, not asked for: nothing is added.

## Acceptance criteria

Rewrite engine, `src/rewrite/http.rs`:

- AC-1. When the server does not answer within the bound, the error message states
  that the reply took longer than 30 seconds, and does not contain "check the
  server is running and the address is correct". It states what to do next.
- AC-2. When the server answers 400 with a body, the error message states that the
  server answered, contains `400`, and contains the body text. It does not
  contain "cannot reach" and does not contain "check the server is running".
- AC-3. A non-2xx status other than 400 (for example 404 or 500) is reported the
  same way as in AC-2, with its own status and body.
- AC-4. When the server answers with a body longer than the bound chosen at
  design, the message contains only a bounded part of it and shows that it was
  cut. A test feeds a body longer than the bound and asserts the message length.
- AC-5. A non-2xx response with an empty body still names the status and says the
  server gave no explanation.
- AC-6. When nothing listens on the port, the error message says the connection was
  refused, names the address, and says what to do next. It is distinguishable in
  text from AC-1 and AC-2.
- AC-7. Every message in AC-1 to AC-6 names the URL that was called.

Transcriber, `src/stt/http.rs`:

- AC-8. AC-1 to AC-7 hold for `src/stt/http.rs` (timeout, non-2xx with body, empty
  body, refused connection), each with a test against a local test double.
- AC-9. A failure to read the take's audio file is reported as that failure and
  names the file, not as an unreachable server. Test: the existing
  missing-file case asserts the message does not contain "cannot reach".

Delivery, `src/delivery.rs`:

- AC-10. When the program named for `herdr` does not exist, the message keeps the
  `PATH` sentence: it names the binary, the `PATH` searched, and
  `HERDR_BIN_PATH`.
- AC-11. When the program exists without the execute bit, the message says it was
  found and could not be run because of permissions, names the file, and says
  what to do next. It does not contain the `PATH` sentence. Test: a fixture
  file without the execute bit (Unix).
- AC-12. When starting the program fails for any other reason, the message contains
  the operating system's own text for the error and names the binary. It does
  not contain the `PATH` sentence.
- AC-13. A program that starts and exits with a failure status still produces
  `DeliveryError::Rejected` with the same content as today.

All:

- AC-14. `cargo test`, `cargo clippy --all-targets -- -D warnings`,
  `cargo fmt --check` and `python3 scripts/check_manifest.py` pass, and the
  Windows dead-code check in the run brief passes.
- AC-15. No test needs a live endpoint or a live herdr.
- AC-16. No panic path is introduced in the daemon.

## Chosen readings

- "Names the bound" (#52) is read as naming the number, 30 seconds, as it is
  defined by the constant, not a literal typed in the message.
- "What to do about it" for a timeout cannot be "raise the bound": the bound is a
  constant, not a configuration key, and the issue puts changing it out of
  bounds. The advice for a timeout is therefore to wait and retry, for example
  while the model loads.
- "Something else" for a binary that is found and cannot be run (#78) is read as
  one message for `PermissionDenied` and one for every other operating-system
  reason, which carries the reason verbatim. Separate messages for
  `ETXTBSY` and resource exhaustion are not required.
- The length bound for the server's explanation is not given by the issues. The
  number is chosen at design.

## Out of scope / noticed

- The 30-second bound itself (#52).
- The flaky test behind #78, and #66.
- `src/doctor.rs`: the same defect exists there; named in the pull request as
  remaining, tracked in #101. `src/stt/command.rs` and `src/rewrite/command.rs`,
  which #78 also lists, already tell `ErrorKind::NotFound` apart from other errors.

## Amendment 2026-09-30 — a 2xx response with no readable text

Added after the code was written and run against a live endpoint. The criteria above
are unchanged.

**As-is.** A server can report a refusal as a 2xx response with an error in the body.
Measured read-only against a local OpenAI-compatible server (LM Studio, port 4000):

```
$ curl -X POST http://127.0.0.1:4000/v1/chat/completionz -H 'Content-Type: application/json' -d '{}'
{"error":"Unexpected endpoint or method. (POST /v1/chat/completionz)"}
HTTP 200
```

The rewrite engine then returns `HttpError::Unreadable` and prints `"<url>" answered
with something this could not read: no choices[0].message.content string in the
response body` (`src/rewrite/http.rs`, the `Unreadable` arms after the request). The
transcriber prints the same shape with `no text string in the response body`
(`src/stt/http.rs`). The server's sentence is discarded, and for a body that is not
JSON it is consumed by `into_json` and lost. This is the defect of #52 on a path the
issue did not measure: the server's own explanation never reaches the person.

**Requirement.** R10. The explanation the server gave is kept on this path as it is on
a non-2xx status (R8). Carried by the run assignment's decision to include it, not by
either issue.

**Acceptance criteria.**

- AC-17. When the rewrite engine receives a 2xx response whose body is not valid JSON,
  or is valid JSON without `choices[0].message.content`, the error message contains the
  same bounded, single-line excerpt of the body as AC-4 describes, introduced by
  "the server said:". A test feeds `{"error":"Unexpected endpoint or method."}` and
  asserts the message contains `Unexpected endpoint or method.`.
- AC-18. A 2xx body that is empty says the body was empty, in place of an excerpt.
- AC-19. AC-17 and AC-18 hold for `src/stt/http.rs` (a 2xx response without a `text`
  string, or whose body is not JSON).
- AC-20. The message still names the URL and still says the answer could not be read.
  A successful response is read exactly as before.

**Out of scope / noticed.** A timeout while the body of a 2xx response is being read
is still reported through the same unreadable-answer message, without a cause of its
own. It is named in the pull request as remaining.
