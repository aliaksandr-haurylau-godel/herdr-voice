# AC_85

## as-is

Every message the plugin has for a person goes through one function, `toast` in
`src/daemon.rs`, which calls `Deliverer::notify`, which runs
`herdr notification show <title> --body <body>` (`src/delivery.rs:221-234`). The
callers are `report_failure` (a failed take, a refused delivery, an unavailable
engine) and `announce_rename` (the notice from #73). `toast` returns early when
`[ui] toasts` is false in the plugin's own configuration
(`src/daemon.rs:710-713`); otherwise an `Ok` from `notify` is the end of it.

`src/doctor.rs` produces findings named `herdr`, `daemon`, `config`, `engine`,
`model`, `rewrite` and `record`. None mentions notifications; the words
`notification` and `toast` do not occur in the file. A finding has a `name`, a
`State` (`ok`, `default`, `missing`, `unused`) and one line of `detail`;
`exit_code` is 1 when any finding is `missing`.

herdr 0.9.1 was asked, by running it, where notifications go. An isolated server
was started with its own `HERDR_CONFIG_PATH` and socket; the owner's server was
not used. Results:

1. **No command or API method reports the setting.** `herdr api schema --json`
   lists the request methods; none reads configuration (the only configuration
   method is `server.reload_config`). `herdr config check` prints `config: ok`
   and nothing else. `herdr status server` and `herdr status client` print the
   version, protocol and socket.
2. **The reply of `herdr notification show` does not identify the setting.**

   | client attached | `delivery` | `reason` | `shown` |
   |---|---|---|---|
   | no | `off` | `disabled` | false |
   | no | `terminal`, `herdr`, `system` | `no_foreground_client` | false |
   | yes, focused | `off`, `terminal`, `herdr`, `system` | `shown` | true |

   With a foreground client the reply is the same for all four values, including
   `off`. A reply of `shown: true` therefore says only that herdr accepted the
   request, which matches the state the issue describes.
3. **The default is `off`.** An empty configuration file and an absent one both
   answer `disabled` with no client attached. `herdr --default-config` documents
   the key as `# delivery = "off"`. A herdr whose file never mentions
   `[ui.toast]` shows the plugin's messages nowhere.
4. **The file is the only source.** herdr's own order for locating it is
   `HERDR_CONFIG_PATH`, then `XDG_CONFIG_HOME/herdr/config.toml`, then
   `~/.config/herdr/config.toml`; `config_path()` in `src/setup.rs:96` already
   resolves it that way. The key is `[ui.toast]` `delivery`, with values `off`,
   `herdr`, `terminal`, `system`.

`doctor` reads the file, not the running server. A server that has not reloaded
its configuration can differ from the file.

## to-be

`doctor` prints one more line, `notifications`, saying where herdr is configured
to send notifications and whether the plugin's own messages can be expected to
arrive. The line names, in the same sentence, the setting that decides it and
the file it is set in. It states what is configured, never that it is in effect.

## requirements

1. A function reads `[ui.toast] delivery` from herdr's configuration file at the
   path `config_path()` gives, and returns one of: `off`, `herdr`, `terminal`,
   `system`, absent, or the reason the file could not be read or parsed. The
   function takes the file's text, not the path, so tests need no file.
2. An absent key, or an absent file where the directory exists, is `off` — herdr's
   documented default, established in point 3 above.
3. A value that is none of the four is reported as such with the value quoted.
4. The finding's state and meaning:
   - `herdr` -> `ok`: herdr is configured to draw the toast itself.
   - `terminal` or `system` -> `warning`: herdr hands the message to the outer
     terminal or the operating system and cannot tell whether it appeared.
   - `off`, absent, unreadable, unparsable, or an unknown value -> `missing`: the
     plugin's messages are not expected to arrive, or it is not known where they go.
   - `[ui] toasts = false` in the plugin's own configuration -> `unused`: the
     plugin is set not to raise toasts, so herdr's setting does not matter. This
     takes precedence over the herdr value.
5. Every line that is not `ok` says what to change and where: the key
   `[ui.toast] delivery = "herdr"`, the file path, and `herdr server reload-config`
   afterwards. The `warning` and `missing` lines also name the plugin log as the
   other place the messages are written.
6. The wording says "configured as" or "set to", never "is". One line, like the
   other findings.
7. `exit_code` keeps its rule: 1 when a finding is `missing`, so `warning` does
   not change the exit code.
8. Nothing is written to herdr's configuration, and the daemon does not raise
   anything new at start.

## acceptance criteria

- **AC-1.** For each of `off`, `herdr`, `terminal`, `system`, an absent key, an
  unknown value, an unparsable file and an unreadable file, a unit test asserts
  the finding's state and that its detail contains the value (or the reason), the
  file path, and for every non-`ok` state `[ui.toast]`, `delivery = "herdr"` and
  `herdr server reload-config`.
- **AC-2.** `[ui] toasts = false` gives `unused` whatever the herdr file says,
  including when the file cannot be read; a test asserts both.
- **AC-3.** `warning` does not make `exit_code` return 1; `missing` does. Tests
  assert both.
- **AC-4.** `doctor` prints the line, in the position after `daemon`, on this
  machine, run against the owner's configuration (`delivery = "herdr"`, read
  only) and against an isolated file set to `terminal`, `off` and absent;
  each output is recorded in `docs/evidence.md`.
- **AC-5.** `docs/evidence.md` records the four probe results of "as-is" with the
  commands, herdr version and platform.
- **AC-6.** `cargo test`, `cargo clippy --all-targets -- -D warnings`,
  `cargo fmt --check`, `python3 scripts/check_manifest.py` and the Windows
  dead-code check pass, the known intermittent tests (#62, #66) excepted.

## Out of scope / noticed

- **Reading of the out-of-bounds clause.** "Changing anyone's herdr configuration,
  or telling them to" forbids the plugin changing the file, and forbids it
  pressing a change on anyone unasked: no toast, no journal line, no message at
  daemon start. `doctor` is run by the person when something is not working;
  there, naming the setting that decides the outcome is what the issue's
  "Done when" asks for ("named there with what to change"). The two are read as
  compatible on that basis.
- No second notification mechanism and no change to `toast`.
- Detecting the running server's setting. herdr offers no way (point 1); a stale
  server is covered by the wording, not by a check.
- The name `notifications` and the wording are proposed to the owner and may
  change; only the strings and their tests change with them.
- `voice-93` adds a `doctor` finding in the same file; the two are independent.
