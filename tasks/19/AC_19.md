# AC_19

## as-is

The daemon answers a client with one `Reply`, and the wire carries it as one
line. `Reply::write_to` writes `ok {text}` or `error {text}` with `writeln!`
(`src/proto.rs:160-161`), so a newline inside `text` becomes a second line on
the wire. `Reply::read_from` reads exactly one line with `read_line` and returns
(`src/proto.rs:167-169`). Nothing on either side checks that the text holds no
newline, and `src/client.rs:1` states the intended shape: "one connection, one
frame, one reply line, exit". The remainder after the first newline is never
read, and the client exits with the code chosen from the first line alone
(`src/client.rs:53-65`).

What a reply carries on `main` at `13733c5` differs from what the issue says,
and the difference matters to how the criteria are worded:

- The success reply after a delivered take is
  `delivered to {target} [{level:.1} dB]` (`src/daemon.rs:986-991`). It does not
  contain the transcript, so a newline in the transcript cannot truncate *this*
  reply. The issue's `{text} [{level} dB, {target}]` is the format from before
  commit `d4a2d1b` ("Deliver the transcript into the pane, unsent") and no longer
  exists.
- The reply for a take whose delivery failed contains the transcript, with
  newlines already replaced by spaces (`src/daemon.rs:1017-1020`), after the
  target, the error text and the path of the kept take.
- The replies for a take that failed before delivery are
  `{why} — the take is kept at {path}` (`src/daemon.rs:901-904` and `:913-916`).
  `why` is not flattened. It can hold a newline in two places read in the code:
  `EngineError::NotConfigured`, whose text is
  `... there is nothing to run. For example:\n  {example}`
  (`src/stt.rs:70-74`), and `CommandError::Failed`, which prints the transcriber's
  standard error after `trim()` and `truncate`, so any line break inside it stays
  (`src/stt/command.rs:151-162`, `:101`). In both cases the client receives the
  first line only, and the text ` — the take is kept at {path}` is in the
  discarded remainder, so the path of the kept recording is lost as well.
- `candle` is built since issue #15, so the issue's `candle` example no longer
  reproduces. The `command` engine with an empty `command` key reproduces the
  same shape.

These points were established by reading the code. None was run for this
assessment; the reproduction is the first test written in S4.

## to-be

A reply whose text contains a newline is either delivered to the client whole,
or refused by the protocol with a message that says it was refused and what to do
next. It is never cut at the newline and reported as a complete reply. A reply
that reaches the client keeps the parts that follow the text: the level and the
target pane on a success, the path of the kept recording on a failure.

## requirements

1. A reply containing a newline does not lose any character after the newline
   between the daemon and the client's output (issue: "Done when", 1).
2. If the design refuses a reply instead, the refusal is visible to the person
   running the client, with exit code 1 (issue: "Done when", 1, "or the protocol
   refuses to send it").
3. On a take whose transcript contains a newline, the target pane and the level
   reach the client's output (issue: "Done when", 2).
4. A refusal message that contains an example delivers the example (issue:
   "Done when", 3).
5. The behaviour is tested through a real round trip of the protocol, not only
   through `Display` (issue: "Done when", 4).

The choice between carrying a multi-line reply whole and refusing to send one is
a design question and is not settled here.

## acceptance criteria

- **AC-1.** With a `Reply::Ok` or `Reply::Error` whose text contains `\n`, the
  client's printed message either equals the full text, or is a refusal that
  states the reply was not delivered and what to do next and is accompanied by
  exit code 1. In neither case does it end at the first `\n` with exit code 0.
- **AC-2.** A take of a two-line transcript, run through the real client and
  daemon over a socket, produces a client output that contains the delivery
  target and the level in dB.
- **AC-3.** A take that fails with the `command` engine configured with an
  empty `command` key produces a client output that contains the word
  `For example:` and the example line that follows it, and the path of the kept
  recording.
- **AC-4.** A take that fails because the transcriber wrote two lines to
  standard error produces a client output that contains both lines and the path of
  the kept recording.
- **AC-5.** A test in `src/` writes a reply with an embedded newline to a socket
  pair with `Reply::write_to` and reads it with `Reply::read_from` (the two real
  functions, over a real transport), and asserts AC-1.
- **AC-6.** A reply without a newline is written and read exactly as before: the
  bytes on the wire for `Reply::Ok("holding for w1:p1")` are unchanged.
- **AC-7.** The four gates of `CLAUDE.md` pass, and the Windows dead-code check
  of the brief passes.

## Out of scope / noticed

- Whether the transcript itself reaches the pane whole when it contains a newline
  belongs to `src/delivery.rs` and to the pane's own handling of input. The issue
  is about the reply and does not cover it, and this assessment did not read that
  path to a conclusion.
- The transcript in the failed-delivery reply has its newlines replaced with
  spaces (`src/daemon.rs:1019`). That is a change of the text, made visibly, and
  the issue does not ask for it to change.
- `src/client.rs:1` and `src/proto.rs` module comments describe the reply shape;
  they are updated only as far as the chosen design requires.
- `Risk` field: not applicable, the trigger is a GitHub issue.
