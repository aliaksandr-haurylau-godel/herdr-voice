# AC_22 — Delivery: put the transcript in the pane without submitting it

Input: GitHub issue 22, `gh issue view 22`, no comments. `docs/design.md` section
4 ("Delivery") and section 7 (configuration, `[delivery]`), `docs/decisions.md`
(the pinned-target-pane entry, 2026-08-25 #8), `docs/evidence.md`, the delivery
half of `spike/spike.sh`, `CLAUDE.md` on silent failure.

Revised after the S1 gate returned `QUESTIONS`, recorded in `tasks/22/RUN_22.md`.
The worktree this artifact was first written against predated pull request #20;
recognition has since landed on `main` and this revision is written against it.

## as-is

Recognition is in and wired. `src/stt.rs` and `src/stt/command.rs` give the daemon
an `Engine` it can transcribe a take with; `src/daemon.rs:80-115` builds one at
start-up and holds the result — engine or reason it could not be built — as
`Recognition`. `dictate` (`src/daemon.rs:90-97`) starts a take on the first
invocation and, on the second, stops the recorder and passes the finished `Take`
to `transcribe` (`src/daemon.rs:100-118`), which calls the engine and replies
`"{text} [{level_dbfs:.1} dB, {target}]"` on success, or, if the engine is missing
or the call fails, `"{why} — the take is kept at {take.path}"`. That reply goes
back to the client only; nothing delivers it anywhere. `capture.rs` defines
`Take { path, level_dbfs, target, .. }` (`src/capture.rs:95-100`); `target` already
carries the pane pinned at the start of the take, per the decision at
`docs/decisions.md:44`.

There is still no `[delivery]` table in `src/config.rs` — `[stt]` and `[rewrite]`
are read there, not `[delivery]` — although `docs/design.md:246-247` already
documents its shape: `submit = false`. Nothing in `src/` calls `herdr pane
send-text`, `herdr agent prompt` or `herdr notification show`; those exist only in
the prototype. The daemon's only "visible failure" channel today is a line to
standard error, which herdr captures and shows through `herdr plugin log list`
(`src/daemon.rs:132,157,169,189,191`, the pattern `request_line` and
`context_note` already follow) — there is no journal or toast subsystem beyond
that; the blinking indicator itself is separate work the issue puts out of bounds.

`docs/evidence.md`, "Delivering into a pane that is gone" (macOS 26.6.2, herdr
0.8.2): against a pane id that does not exist, `herdr pane send-text` refuses with
`{"error":{"code":"pane_not_found",...}}`, exit 1, and `herdr agent prompt`
refuses with `{"error":{"code":"agent_not_found",...}}`, exit 1. Both are ordinary
rejected calls, not a silent success and not a hang.

The prototype's delivery, `spike/spike.sh:345-352`:

```
deliver() { # $1=text
  if [ "$SUBMIT" -eq 1 ] && [ -n "${TARGET_AGENT:-}" ]; then
    herdr agent prompt "$TARGET" "$1" >/dev/null || die "herdr agent prompt rejected the text"
  else
    herdr pane send-text "$TARGET" "$1" >/dev/null || die "herdr pane send-text rejected the text"
  fi
}
```

`TARGET_AGENT` is looked up from `herdr pane list` at take-start time
(`spike/spike.sh:145`) and stashed with the run's state alongside `TARGET`
(`spike/spike.sh:263`) — so submitting is gated on the pinned pane actually
running an agent, checked once, at the same moment the pane itself is pinned. This
project's own `Invocation` already carries the equivalent field, captured at that
same moment: `focused_pane_agent: Option<String>` (`src/context.rs:14`), read once
per take when `context::parse` runs in `answer` (`src/daemon.rs:56`).

`die()` (`spike/spike.sh:95`) logs the reason to the run log, shows a toast and
exits before the line that removes the take's WAV file (`spike/spike.sh:466`,
`544`) runs — so a failed delivery in the prototype leaves the WAV on disk, by the
accident of `exit 1` skipping the cleanup line, not by a stated rule. The
transcribed text is written to the same log one line earlier, before `deliver` is
called at all (`spike/spike.sh:448`: `log "ptt transcribed ...: ${RAW}"`), so the
text is not only in the process's memory when delivery is attempted.

## to-be

A take that finishes transcribing has its text delivered, not merely returned:
inserted into the pinned pane's input and left there unsent, by default;
submitting it is opt-in through configuration, and falls back to inserting when
the pinned pane has no agent to submit to. The pane is the one pinned when the
take began, never one recomputed at delivery time. A delivery that cannot
complete — the pane gone, the call rejected for any other reason — is visible: a
journal line and a toast, and neither the text nor the take's audio is silently
lost. What the client is told on a finished take changes with it: a successful
delivery is confirmed by where the text went, not repeated in full; a failed one
carries both the text and the reason, since the pane never got either.

## Requirements

Asked for by the issue:

- R1 The text is inserted into the pinned pane's input and not submitted, so
  several takes can be stacked and sent by hand — the default path.
- R2 Submitting is reachable only behind an explicit, non-default setting, never
  on the default path.
- R3 The pane used is the one pinned when the take began, held until delivery —
  not one recomputed at delivery time.
- R4 A failed delivery is visible: a journal line and a toast.
- R5 A failed delivery must not make the text disappear without a trace.

Implied, and in scope only as far as R1 to R5 need them:

- R6 `herdr pane send-text <pane> <text>` is the call used on the default,
  unsent path; `herdr agent prompt <pane> <text>` is the call used only when
  submitting is turned on, since it appends Enter. Both facts are given, not
  derived here.
- R7 A `[delivery]` configuration table with a `submit` key, default `false` —
  the shape `docs/design.md:246-247` already documents. R2 needs a default, and
  every other configuration key in this project has one (`CLAUDE.md`).
- R8 A rejected `herdr pane send-text` or `herdr agent prompt` call is the one
  failure mode delivery has, whatever the reason herdr gives — a gone pane
  included, per the measurement in `docs/evidence.md`. R4 and R5 apply to it
  exactly as to any other rejected call; nothing separate is needed to detect a
  gone pane in advance.
- R9 No panic path in delivery, and the failure message names what to do next
  (`CLAUDE.md`, "Rules for the code").
- R10 Delivery is called from the take that produced the text, with that text —
  a piece of the pipeline that nothing calls does not put text in anybody's
  input, which is the issue's stated goal. This determines what `dictate`'s
  reply becomes on both a successful and a failed take (R11, R12).
- R11 On a successful delivery, the reply to the client confirms where the text
  went, not the text itself — it already reached the pane.
- R12 On a failed delivery, the reply to the client carries both the text and
  the reason. `CLAUDE.md` rates a silent failure as a defect of the same weight
  as a wrong transcript, and here the text reached neither the pane nor the
  screen unless the reply carries it.

## Chosen readings

1. **What "text" delivery receives, revised.** The first version of this artifact
   was written against a worktree that predated pull request #20 and read
   transcription as out of this branch; it is not. Recognition is in `main` and
   `dictate` already produces real text on a finished take (`src/daemon.rs:100-118`).
   Delivery is therefore in scope as a called stage, not only a tested module: R10
   below. Testing it still needs no live herdr — `CLAUDE.md` describes this stage's
   testing as "delivery through a recorded call," and that stands regardless of
   who calls it.
2. **What "journal" means here.** No journal subsystem exists in `src/`. Every
   existing "visible failure" in the daemon is a line on standard error, captured
   by herdr's own plugin log (`request_line`, `context_note`). AC-8 reads
   "journal line" as one more line in that same channel, not a new one.
3. **What makes the take's text recoverable after a failed delivery.** The take
   produces no separate text file; the only artifact on disk is the WAV
   (`capture.rs::Take.path`). "The text must not be lost silently, and the person
   must be able to get it" is met three ways at once, and all three are written as
   AC rather than treating one alone as sufficient: the text is written to the
   journal line before delivery is attempted, the client's own reply on a failed
   delivery carries the text directly (R12), and the WAV is kept rather than
   deleted so the take itself is not lost either.
4. **Whether `submit = true` always uses `herdr agent prompt`.** It does not.
   The prototype gates that call on the pinned pane actually running an agent and
   falls back to `send-text` otherwise (`spike/spike.sh:348`, `TARGET_AGENT`
   looked up when the pane is pinned). The reason to keep that condition rather
   than drop it: without it, turning `submit` on breaks delivery into any pane
   that is not an agent — a plain shell, say — even though inserting the text
   there works fine; that is a regression the issue does not ask for and the
   prototype does not have. The condition is cheap to keep here, more so than in
   the prototype: `Invocation.focused_pane_agent` (`src/context.rs:14`) already
   carries the same fact, captured at the same moment the target pane itself is
   pinned, so no extra herdr call is needed to restore it. Restored as AC-4 below.

## Acceptance criteria

- **AC-1** `[delivery] submit` is read from the configuration with a default of
  `false`. An absent configuration file, or a file that omits `[delivery]`
  entirely, leaves `submit` at `false`.
- **AC-2** A take that finishes transcribing successfully has its text delivered:
  `dictate`'s second invocation, after a successful `transcribe`, calls delivery
  with that text and the pinned target — delivery is reached in the running
  daemon, not only from a test.
- **AC-3** When `submit` is `false`, delivery inserts the text into the pinned
  pane with `herdr pane send-text <pane> <text>` and does not submit it: nothing
  in the delivery path sends Enter.
- **AC-4** When `submit` is `true` and the pinned pane has an agent (the take's
  invocation named one in `focused_pane_agent`), delivery submits the text with
  `herdr agent prompt <pane> <text>` instead of `herdr pane send-text`. When
  `submit` is `true` and the pinned pane has no agent, delivery falls back to
  `herdr pane send-text`, as it does when `submit` is `false`.
- **AC-5** The pane delivery targets is the one pinned when the take began
  (`Take.target`); nothing about delivery recomputes the target pane from
  current focus.
- **AC-6** Any rejection of the underlying `herdr pane send-text` or `herdr
  agent prompt` call — including the pane no longer existing, measured in
  `docs/evidence.md` to fail with `pane_not_found` or `agent_not_found` and exit
  1 — is treated as a failed delivery. No existence check runs before the call;
  the rejection is the failure signal.
- **AC-7** A failed delivery writes a line to the daemon's standard error, in the
  same channel `herdr plugin log list --plugin haurylau.voice` already shows,
  naming the target pane and the reason.
- **AC-8** A failed delivery shows a toast (via `herdr notification show` or
  equivalent) that names that the delivery failed.
- **AC-9** The text handed to delivery is written to the daemon's standard error
  before the delivery attempt is made, so a failed delivery still leaves the text
  visible in the journal, not only held in memory.
- **AC-10** On a failed delivery, the take's audio file (`Take.path`) is not
  deleted.
- **AC-11** On a successful delivery, the reply the client prints confirms the
  target pane and the measured level; it does not repeat the delivered text in
  full, since the text already reached the pane.
- **AC-12** On a failed delivery, the reply the client prints carries both the
  full text that failed to deliver and the reason it failed — the person reading
  the client's own output has both without going to the journal.
- **AC-13** Delivery has no panic path: a rejected call and any other failure
  each produce an error result and a message naming the reason, never a process
  abort.
- **AC-14** Delivery is covered by tests that exercise the insert-only path, the
  submit path, the submit-falls-back-to-insert path, and a rejected-call failure,
  against a fake or recorded pane call — none of them needs a live herdr or a
  real pane. A dedicated fake for "pane does not exist" is not needed: AC-6
  covers it as one instance of a rejected call.

## Out of scope / noticed

- Push-to-talk and the indicator — the issue puts both out of bounds explicitly.
- Rewriting the text before delivery — out of bounds explicitly.
- Context-biased recognition (issue 21) — a separate, open issue; delivery takes
  whatever text `transcribe` produces today.
- A CLI flag for `submit`, distinct from the configuration key. The design's
  documented shape (`docs/design.md:246-247`) is a configuration key only, and
  the issue does not ask for a command-line override.
- Whether the toast in AC-8 also names the reason, beyond that a delivery
  failed. Nothing in the issue or `docs/design.md` distinguishes the toast's
  content from the journal line's; AC-7 covers the reason explicitly, AC-8 does
  not repeat that requirement for the toast.
- The exact wording of the confirmation reply in AC-11 and the failure reply in
  AC-12. Both are left to design; the criteria state what each must convey, not
  the string.
