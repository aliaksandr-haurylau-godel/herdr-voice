# AC_22 — Delivery: put the transcript in the pane without submitting it

Input: GitHub issue 22, `gh issue view 22`, no comments. `docs/design.md` section
4 ("Delivery") and section 7 (configuration, `[delivery]`), `docs/decisions.md`
(the pinned-target-pane entry, 2026-08-25 #8), `docs/evidence.md`, the delivery
half of `spike/spike.sh`, `CLAUDE.md` on silent failure.

## as-is

The pipeline stops after capture. `src/daemon.rs:79-93` (`dictate`) starts a take
on the first invocation and, on the second, stops the recorder and replies with
the take's own path, level and target — there is no transcription, no rewrite and
no delivery stage yet; issues 13, 15, 16 and 21 are open and unmerged. `capture.rs`
defines `Take { path, level_dbfs, target, .. }` (`src/capture.rs:95-100`); `target`
already carries the pane pinned at the start of the take, per the decision at
`docs/decisions.md:44`. There is no `[delivery]` table in `src/config.rs` — only
`[stt] model`, `[rewrite] engine` and `[rewrite] agent` are read there — although
`docs/design.md:246-247` already documents its shape: `submit = false`.

Nothing in `src/` calls `herdr pane send-text`, `herdr agent prompt` or `herdr
notification show`; those exist only in the prototype. The daemon's only "visible
failure" channel today is a line to standard error, which herdr captures and shows
through `herdr plugin log list` (`src/daemon.rs:132,157,169,189,191`, the pattern
`request_line` and `context_note` already follow) — there is no journal or toast
subsystem beyond that; the blinking indicator itself is separate work the issue
puts out of bounds.

The prototype's delivery, `spike/spike.sh:345-352`:

```
deliver() { # $1=text
  if [ "$SUBMIT" -eq 1 ] && [ -n "${TARGET_AGENT:-}" ]; then
    herdr agent prompt "$TARGET" "$1" >/dev/null || die "herdr agent prompt rejected the text"
  else
    herdr pane send-text "$TARGET" "$1" >/dev/null || die "herdr pane send-text rejected the text"
  fi
}
```

`die()` (`spike/spike.sh:95`) logs the reason to the run log, shows a toast and
exits before the line that removes the take's WAV file (`spike/spike.sh:466`,
`544`) runs — so a failed delivery in the prototype leaves the WAV on disk, by the
accident of `exit 1` skipping the cleanup line, not by a stated rule. The
transcribed text is written to the same log one line earlier, before `deliver` is
called at all (`spike/spike.sh:448`: `log "ptt transcribed ...: ${RAW}"`), so the
text is not only in the process's memory when delivery is attempted.

## to-be

Once a piece of text is ready to be delivered to a pane, it is inserted into that
pane's input and left there unsent, by default; submitting it is opt-in through
configuration. The pane is the one pinned when the take began, never one
recomputed at delivery time. A delivery that cannot complete — pane gone, or the
underlying herdr call rejected — is visible: a journal line and a toast, and the
text and the take's audio are not silently lost.

## Requirements

Asked for by the issue:

- R1 The text is inserted into the pinned pane's input and not submitted, so
  several takes can be stacked and sent by hand — the default path.
- R2 Submitting is reachable only behind an explicit, non-default setting, never
  on the default path.
- R3 The pane used is the one pinned when the take began, held until delivery —
  not one recomputed at delivery time.
- R4 A failed delivery is visible: a journal line and a toast.
- R5 A failed delivery must not make the text disappear without a trace.

Implied, and in scope only as far as R1 to R5 need them:

- R6 `herdr pane send-text <pane> <text>` is the call used on the default,
  unsent path; `herdr agent prompt <pane> <text>` is the call used only when
  submitting is turned on, since it appends Enter. Both facts are given, not
  derived here.
- R7 A `[delivery]` configuration table with a `submit` key, default `false` —
  the shape `docs/design.md:246-247` already documents. R2 needs a default, and
  every other configuration key in this project has one (`CLAUDE.md`).
- R8 The pane no longer existing by the time delivery runs (closed, or its
  process exited) is one of the ways delivery can fail, not a separate case the
  issue distinguishes — R4 and R5 apply to it exactly as to any other failure.
- R9 No panic path in delivery, and the failure message names what to do next
  (`CLAUDE.md`, "Rules for the code").

## Chosen readings

1. **What "text" delivery receives.** The issue frames delivery in terms of a
   "finished take" landing as text, but transcription and rewrite (issues 13, 15,
   16, 21) are not part of this branch and are out of this ticket's bounds by
   omission — the issue's own "Out of bounds" list only names push-to-talk, the
   indicator and rewriting the text, and none of those is transcription. These
   AC treat delivery as an operation over a pane and a piece of text, testable
   with a fake pane call and a literal string, per `CLAUDE.md`'s own description
   of how this stage is tested: "delivery through a recorded call." Wiring a real
   transcript into that call is not blocked by anything in this ticket, but it
   cannot be demonstrated end-to-end until a transcription stage exists to
   produce the text; that gap is recorded under "Out of scope / noticed," not
   folded into an AC.
2. **What "journal" means here.** No journal subsystem exists in `src/`. Every
   existing "visible failure" in the daemon is a line on standard error, captured
   by herdr's own plugin log (`request_line`, `context_note`). AC-7 reads
   "journal line" as one more line in that same channel, not a new one.
3. **What makes the take's text recoverable after a failed delivery.** The take
   produces no separate text file; the only artifact on disk is the WAV
   (`capture.rs::Take.path`). Read literally, "the text must not be lost
   silently, and the person must be able to get it" is met two ways at once: the
   text itself is written to the journal line before delivery is attempted (so
   it is recoverable from the log even if the pane is gone), and the WAV is kept
   rather than deleted so the take is not lost either. Both are written as AC
   below rather than treating either alone as sufficient.

## Acceptance criteria

- **AC-1** `[delivery] submit` is read from the configuration with a default of
  `false`. An absent configuration file, or a file that omits `[delivery]`
  entirely, leaves `submit` at `false`.
- **AC-2** When `submit` is `false`, delivery inserts the text into the pinned
  pane with `herdr pane send-text <pane> <text>` and does not submit it: nothing
  in the delivery path sends Enter.
- **AC-3** When `submit` is `true`, delivery submits the text with `herdr agent
  prompt <pane> <text>` instead of `herdr pane send-text`.
- **AC-4** The pane delivery targets is the one pinned when the take began
  (`Take.target`); nothing about delivery recomputes the target pane from
  current focus.
- **AC-5** A delivery attempt against a pane that no longer exists — closed, or
  its process exited since the take began — is treated as a failed delivery
  (AC-6, AC-7, AC-8), not as a silent no-op and not as a panic.
- **AC-6** Any failure of the underlying `herdr pane send-text` or `herdr agent
  prompt` call, for any reason, is treated as a failed delivery.
- **AC-7** A failed delivery writes a line to the daemon's standard error, in the
  same channel `herdr plugin log list --plugin haurylau.voice` already shows,
  naming the target pane and the reason.
- **AC-8** A failed delivery shows a toast (via `herdr notification show` or
  equivalent) that names that the delivery failed.
- **AC-9** The text handed to delivery is written to the daemon's standard error
  before the delivery attempt is made, so a failed delivery still leaves the text
  visible in the journal, not only held in memory.
- **AC-10** On a failed delivery, the take's audio file (`Take.path`) is not
  deleted.
- **AC-11** Delivery has no panic path: a missing pane, a rejected call and any
  other failure each produce an error result and a message naming the reason,
  never a process abort.
- **AC-12** Delivery is covered by tests that exercise both the insert-only path
  and the submit path, and the pane-gone / call-rejected failure path, against a
  fake or recorded pane call — none of them needs a live herdr or a real pane.

## Out of scope / noticed

- Push-to-talk and the indicator — the issue puts both out of bounds explicitly.
- Rewriting the text before delivery — out of bounds explicitly.
- Producing the text delivery receives: transcription (issue 13, 15, 16) and
  context-biased recognition (issue 21) are separate, open issues and not part
  of this branch. This ticket's scope is the delivery operation itself, per
  "Chosen readings" above; wiring `dictate`'s reply to actually invoke it with a
  real transcript depends on that text existing, which it does not yet in this
  worktree.
- A CLI flag for `submit`, distinct from the configuration key. The design's
  documented shape (`docs/design.md:246-247`) is a configuration key only, and
  the issue does not ask for a command-line override.
- Whether the toast in AC-8 also names the reason, beyond that a delivery
  failed. Nothing in the issue or `docs/design.md` distinguishes the toast's
  content from the journal line's; AC-7 covers the reason explicitly, AC-8 does
  not repeat that requirement for the toast.
