# AC_90

## as-is

`CpalSource::start` in `src/capture/cpal_source.rs` picks a stream
configuration with `pick_config`, reads its `sample_format()` and builds an
input stream in a `match`. Two arms exist: `cpal::SampleFormat::F32`, which
pushes the samples through unchanged, and `cpal::SampleFormat::I16`, which
divides each sample by `i16::MAX` (`src/capture/cpal_source.rs:78-96`). Every
other format falls into the `other =>` arm and the take is refused with
`"<device>" delivers <format> samples, which this build does not read`
(`:97-101`).

On the machine issue #90 was filed from — Windows 11, release `v0.1.0-beta.3`
installed through `herdr plugin install`, default input
`Microphone Array (Realtek(R) Audio)` — that arm is the one reached. Two
`dictate` invocations, started and stopped by hand, both failed with exit 1
and this on standard error, read from `herdr plugin log list --plugin herdr-voice`:

```
"Microphone Array (Realtek(R) Audio)" delivers I24 samples, which this build does not read
```

Held through the push-to-talk binding, the same input produced `ptt` runs that
all exited 0. Fourteen simulated repeats gave some replies `holding for w4:p2`
and the rest `the daemon did not answer within 2 seconds`; the tab label never
carried the recording marker. herdr's own configuration on that machine has
`[ui.toast] delivery = "terminal"`, which is the state #85 describes: the
refusal was raised as a toast and nothing reached the screen.

The pinned dependency is `cpal = "0.18"` (`Cargo.toml:24`), resolving to 0.18.2.
That release exposes the format as `cpal::SampleFormat::I24` and the sample
type as `cpal::I24`, re-exported from `dasp_sample` 0.11. `I24::inner()` returns
the signed value as an `i32` in `-8_388_608..=8_388_607`; `dasp_sample`'s own
conversion to `f32` divides it by `8_388_608.0` (checked in the crate source,
`dasp_sample-0.11.0/src/conv.rs`, `conversions!(I24, i24 { ... s to_f32 ...`).

Nothing in `src/capture/cpal_source.rs` is unit tested: the file is the one
place that knows what a sound card is, and its header says so. What it produces
is `Event::Samples(Vec<f32>)`, which everything above it tests through a fake.

## to-be

A device whose chosen configuration delivers 24-bit integer samples is opened
like any other. Its samples reach the recorder as `f32` in `-1.0..=1.0`, scaled
the way `dasp_sample` scales them, and a take on that device proceeds to the
same checks — level, silence floor, recognition — as a take on an `F32` or
`I16` device.

## requirements

1. `CpalSource::start` builds an input stream for `cpal::SampleFormat::I24`
   and pushes `Event::Samples` carrying each sample converted to `f32`.
2. The conversion divides the sample's `inner()` value by `8_388_608.0`, so
   `-8_388_608` maps to exactly `-1.0`, `0` to `0.0`, and `8_388_607` to just
   under `1.0`.
3. The conversion is a function that takes a sample and returns an `f32`,
   callable without a device, so a test can pin it.
4. The `other =>` refusal stays for every format still not read, and its text
   is unchanged for them.
5. `docs/evidence.md` records a take from a real 24-bit input on Windows, or
   says plainly that it could not be made.

## acceptance criteria

- **AC-1.** On a device offering only 24-bit integer configurations,
  `CpalSource::start` returns `Ok(Format { .. })` instead of the
  `does not read` refusal. Verified by a take on the affected machine, not by
  reading the diff.
- **AC-2.** A unit test asserts the conversion at both ends of the range and at
  zero: `I24::new(-8_388_608)` gives `-1.0`, `I24::new(0)` gives `0.0`, and
  `I24::new(8_388_607)` gives `8_388_607.0 / 8_388_608.0`. The test fails if the
  divisor is changed to `8_388_607.0` and if the sign handling is dropped.
- **AC-3.** A format this build still does not read — for example
  `cpal::SampleFormat::U16` — reaches the same `other =>` arm and produces the
  same sentence as before this change. This is by construction of the `match`
  and is checked by reading the arm, since no device offering only that format
  can be summoned in a test.
- **AC-4.** `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check` and
  `python3 scripts/check_manifest.py` pass; `cargo test` fails no test that passed
  on unmodified `main` and passes the three new ones; and the Windows CI job
  compiles the change. On this machine `cargo test` is not green at the baseline
  (three `bias::` tests, see `RUN_90.md`), so "passes" is not claimable and is not
  claimed.
- **AC-5.** `docs/evidence.md` carries a section with the platform, the device
  name, and the outcome of a take from the affected input — success, or the
  exact failure that came next.

## Out of scope / noticed, not turned into a criterion

- Every other sample format (`I32`, `U16`, `F64`, ...). Each is its own
  decision; this ticket is the one that was met on a real machine.
- Making a refusal visible when `[ui.toast] delivery` swallows the toast. That
  is #85, and it is the reason the person saw nothing.
- The `ptt` replies `the daemon did not answer within 2 seconds`. They were
  observed while the device was being refused and while a `dictate` test had
  just failed twice on the same daemon; whether they are a consequence of the
  refusal or a separate defect is not established. If a take on a supported
  input still shows them, that is a new issue.
- Recognition. The same machine reports `engine missing` in `doctor`, because
  `[stt] command` is empty and no model is installed. A take that captures
  correctly will meet that next; it is configuration, not this defect.
- The plugin's `mic --choose` pane and device selection by name. Untouched.

## Risk

Not tracked in an ADO `Risk` field — the trigger is a GitHub issue
(`CLAUDE.md`, "Trigger and run root"). The change is confined to one match arm
and one pure function in the file that owns the sound card.
