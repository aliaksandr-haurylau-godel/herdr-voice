# AC_42

Installing the plugin puts a working binary on a machine that has no Rust
toolchain. Issue #42 is the ticket.

## as-is

**The manifest compiles from source on every platform.** `herdr-plugin.toml:11-17`
holds two `build` entries and both run `cargo build --release` — `sh -c` for
macOS and Linux, `cmd /c` for Windows. Nothing in the repository fetches a
release archive.

**The comment above them describes something that was never written.**
`herdr-plugin.toml:7-9`: "From a checkout the binary is built locally; a released
copy fetches the archive for the platform instead. Both leave the binary at the
same path, so every entry below is platform-independent." `docs/design.md:346-349`
says the same: "the manifest's `build` entries fetch the archive that matches the
platform."

**The release workflow builds and publishes archives, and publishes no digest.**
`.github/workflows/release.yml:19-23` cross-builds five targets —
`aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`,
`aarch64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`. `:32-44` packages each as
`herdr-voice-<tag>-<target>.tar.gz`, whose single top-level directory
`herdr-voice-<tag>-<target>/` holds the binary, `README.md` and `LICENSE`. `:61`
is `gh release create "$GITHUB_REF_NAME" dist/*.tar.gz --repo "$GITHUB_REPOSITORY"
--generate-notes` — the archives and nothing else. There is no `.sha256`, no
`SHA256SUMS`, no digest of any kind in the published set.

**No release has ever been published, and no tag has ever been cut.** Run on
2026-09-16 against the repository: `gh api repos/:owner/:repo/releases --jq
'length'` answers `0`, `gh api repos/:owner/:repo/tags --jq 'length'` answers
`0`, and `gh run list --workflow release.yml` prints nothing. `README.md:38`
already records this: "Not yet installable. When the first release is tagged".
So the issue's "the archives exist on every tagged release" is true of the
workflow and not yet true of the repository — there is nothing published for a
`build` entry to fetch today.

**The version is `0.0.0` in two files that must agree.** `herdr-plugin.toml:3`
and `Cargo.toml:2` are both `version = "0.0.0"`, and `scripts/check_manifest.py`
fails when they differ: it reads the crate version out of `Cargo.toml` and
compares, failing with "version X does not match the crate's Y".

### What herdr actually does with a `build` entry

From herdr's own plugin documentation for the installed version, 0.9.0
(`herdr --version` reports `herdr 0.9.0`; the document is
`docs/next/website/src/content/docs/plugins.mdx` at tag `v0.9.0`, section "Build
commands"), and from the installed plugins on this machine. Each of these
decides what the build script can be:

- **Build commands run on `herdr plugin install` only.** "Build commands run
  during GitHub `plugin install` after confirmation and before Herdr registers
  the plugin… `plugin link` does not run build commands; local authors build
  their working tree themselves." So replacing `cargo build --release` in the
  manifest does not change local development at all: `herdr plugin link .`, which
  `CLAUDE.md` and `README.md:63` both name, never ran that entry.
- **A failed build aborts the install.** "If a build command fails, install
  aborts and the plugin is not registered." herdr offers no fallback of its own,
  so the fallback the ticket asks for has to be inside our script, and the script
  has to exit 0 for the install to survive.
- **Build commands get no herdr environment.** "Build commands are plain argv
  commands too, but they do not receive runtime plugin context or Herdr socket
  env." `HERDR_PLUGIN_ROOT`, `HERDR_BIN_PATH` and the rest exist for runtime
  commands only (same document, "Commands and environment"). A build script
  cannot read the plugin root out of the environment.
- **The script must not rewrite the manifest.** "changing `herdr-plugin.toml`
  after the install preview aborts install."
- **`command` is argv, not a shell line.** "Herdr does not run them through a
  shell, so there is no shell expansion unless your command starts a shell
  itself."
- **Failures are reported with the plugin id, build index, working directory,
  command, exit status and capped stdout/stderr.** So a message the script prints
  before exiting non-zero does reach the person.
- **`herdr plugin install` takes `owner/repo[/subdir]` and clones with git**, with
  `--ref` to pin a revision and `--yes` for a non-interactive install
  (`herdr plugin install --help`, run on 2026-09-16). The checkout is stored
  under `~/.config/herdr/plugins/github/<plugin-id>-<hash>/`.

**The clone carries no tags, so the script cannot learn its own tag from git.**
Checked on 2026-09-16 in a plugin herdr installed from GitHub on this machine
(`~/.config/herdr/plugins/github/persiyanov.reviewr-e87b654a74f8`):
`git describe --tags` answers `fatal: No names found, cannot describe anything`,
`git tag` prints nothing, and `.git/shallow` exists. The only in-repository
statement of which release this checkout belongs to is the manifest's `version`.

**Two installed plugins already do this, and they are the working precedents.**
`ranolp.handsfree` fetches in one manifest line — its `[[build]]` is
`["sh", "-c", "mkdir -p target/release && curl -fsSL https://github.com/…/releases/download/v0.2.0/herdr-handsfree-v0.2.0-aarch64-apple-darwin.tar.gz | tar xz -C target/release"]`,
with the version and the platform written into the line and no digest check.
`persiyanov.reviewr` runs `["bash", "herdr/install.sh"]`, a script in its own
repository that derives the tag as `v<version>` from its manifest, maps
`uname -s`/`uname -m` to a target triple, downloads the archive and a `.sha256`
sidecar, compares the digest with `sha256sum` or `shasum -a 256`, and prints a
named message and exits 1 for a platform it has no binary for. It resolves its
own root from `dirname "$0"` and says in a comment why: "build commands may not
receive the runtime env".

**The container check that exists is the `link` path with a toolchain.**
`scripts/linux-check.sh` installs system packages, then rustup and cargo
(`:228`), installs herdr from `https://herdr.dev/install.sh` (`:250`), builds with
`cargo build --release` (`:309`) and links with `herdr plugin link .` (`:333`).
Nothing in it exercises `herdr plugin install`, and every run of it has a Rust
toolchain by construction.

**The repository already verifies a download against a digest elsewhere.** The
`model` command "downloads the one you pick and verifies it against a pinned byte
count and digest before anything loads it" (`README.md:53-55`).

## to-be

`herdr plugin install aliaksandr-haurylau-godel/herdr-voice` on a machine with no
Rust toolchain fetches the archive built for that machine's operating system and
architecture from the release the checkout belongs to, refuses to install
anything whose bytes do not match a digest published beside it, and leaves the
binary where the manifest's `startup`, `actions` and `panes` entries already look
for it. Where no archive can be had, the install falls back to building from
source and says in one line why it is doing that. Where it cannot tell, it stops
and says to retry rather than compiling for an hour nobody asked for. The archives
this is proved against are published by this run, under a tag that reads as a
test and not as a version. The manifest no longer claims something that is not
true.

## requirements

What the ticket asks for:

1. **The `build` entries fetch and unpack the archive for the running platform**
   from the release that checkout belongs to.
2. **What was fetched is verified against a digest published with it.** This is
   not satisfiable against the release workflow as it stands — `release.yml:61`
   publishes archives and no digest — so publishing the digest is part of this
   issue, implied by the requirement rather than written in it.
3. **A source build is the fallback, with a message naming why**, when no archive
   matches the platform — and only then; see the readings below for what a
   network failure does instead.
4. **A from-scratch install with no Rust toolchain is verified in a container**
   and recorded in `docs/evidence.md`, the way `scripts/linux-check.sh` already
   verifies the `link` path.
5. **The comment at `herdr-plugin.toml:7-9` becomes true or goes**, and with it
   the sentence in `docs/design.md:346-349` that says the same thing, since the
   ticket's complaint is against both.

What the ticket implies, and why:

6. **The binary lands at `target/release/herdr-voice`** (`.exe` on Windows),
   because that is where every other manifest entry looks for it —
   `herdr-plugin.toml:21`, `:25`, `:32`, `:39`, `:46`, `:53`, `:61`, `:69`,
   `:77`. Moving the binary elsewhere would mean editing entries the ticket does
   not ask to edit.
7. **`herdr plugin link .` keeps working unchanged**, because herdr never runs
   build entries for a linked plugin. Nothing in the ticket touches local
   development and nothing may break it.
8. **The fetch runs with no herdr environment and no shell expansion**, from the
   checkout, resolving its own root from its own location.

## The readings chosen where the ticket can be read two ways

**Which release a checkout fetches from: `v<version>` out of the manifest.** The
ticket says "from the tagged release" without saying how a checkout knows which
one. The clone is shallow and tagless, so git cannot answer; the manifest's
`version` is the only statement of it inside the checkout. So the tag is `v` plus
`herdr-plugin.toml`'s `version`, which is what `persiyanov.reviewr` does. The
alternative — always fetching the latest release — was not chosen, because it
installs code that is not the code that was cloned.

This creates a rule the release process must keep from now on: a tag `vX.Y.Z` is
cut from a commit whose manifest says `X.Y.Z`. Nothing in the repository enforces
it today and nothing did before. `scripts/check_manifest.py:32-35` compares the
manifest's version with the crate's and never looks at a tag; `release.yml` takes
`GITHUB_REF_NAME` for the archive name at `:36` and the release name at `:61` and
checks it against nothing. A tag that disagreed with the manifest would pass every
gate. The rule is a property of the mechanism this issue builds — the script can
only ask for what the manifest tells it, while the archive is named after the tag
— and not an inheritance from anywhere.

**A digest mismatch fails the install; it does not fall back.** The ticket's
fallback is for "when no archive matches the platform". An archive that was
fetched and whose bytes are wrong is a different event, and falling back there
would make the verification decorative. So: no archive for this platform, or no
such release → fall back with a message. Archive fetched and digest does not
match → fail, and say so.

**"No archive matches the platform" includes "no release exists at all".**
Installing from a reference whose manifest names a version no release was cut
for has to land somewhere, and the only sensible place is the fallback.

**A network failure is not that case, and stops the install.** Only a 404 — no
release with that tag, or a release without that target — falls back to a source
build. A timeout, a name-resolution failure or a 5xx stops the install with a
message saying to retry. Falling back there would start the `candle` compile this
issue exists to avoid, and nobody asked for it.

**Two separate rules, not one.** A 404 is not reliably "no such archive": GitHub's
content delivery network answers 404 for some minutes after a release publishes,
which is why `persiyanov.reviewr` retries with `--retry-all-errors`. So the fetch
retries a bounded number of times with a gap, and only a 404 that survives the
retries counts. The retry decides *whether we know*; the 404 rule decides *what we
do once we know*. Collapsing them reintroduces exactly the hazard the 404 rule was
written to prevent — a CDN that has not caught up, mistaken for a missing target,
answered with an hour-long build.

## What this stage hands to design, undecided

**Where the fetch logic lives.** One `sh -c` line per platform in the manifest,
in the shape `ranolp.handsfree` uses, or a script in the repository that the
manifest calls, in the shape `persiyanov.reviewr` uses. The second is what makes
a digest check, an architecture map and a fallback message expressible at all;
the first is what keeps the repository free of a second implementation of the
same thing. Design chooses and says why. Windows has no `sh`, so whatever is
chosen is answered twice.

**What form the digest takes.** A `.sha256` sidecar per archive, or one
`SHA256SUMS` for the release. Both are changes to `release.yml`.

**Whether the Linux archives stay `-gnu`.** They are built on `ubuntu-latest` and
`ubuntu-24.04-arm` against glibc, so they will not run on a musl image. This
decides which container the check in AC-6 can use, and whether a musl target is
added to the matrix. The ticket does not ask for a musl target; design may say
the check uses a glibc image and leave the matrix alone.

**What the fallback does when `cargo` is also absent.** That is the case the
ticket exists for, and the message herdr shows on a failed build is the last
thing the person sees.

**How `release.yml` marks the `v0.0.0` prerelease.** `gh release create` at `:61`
passes neither `--prerelease` nor `--latest=false`, so as it stands a `v0.0.0`
tag would publish as the repository's latest release. Design chooses between a
rule in the workflow — which tags publish as a prerelease — and an edit made by
hand after the workflow runs. Checked on 2026-09-16: `gh release create` offers
both `-p, --prerelease` and `--latest=false`, and `--generate-notes` has no
trouble with a repository that has never had a release; the generate-notes API
called for `tag_name=v0.0.0` returned notes covering every merged pull request.

**How long the 404 window after publishing actually lasts.** AC-4a requires a
bounded retry and does not say how many. The number should come from watching
the `v0.0.0` archives become fetchable in AC-6a rather than from another
project's comment; design states the budget and where the number came from.

## Out of scope / noticed, not turned into a criterion

- **The first real release of the plugin.** Decided by the owner on 2026-09-16:
  this issue does not cut it, and no version number moves —
  `herdr-plugin.toml:3` and `Cargo.toml:2` both stay at `0.0.0`. What this issue
  publishes instead is a disposable pre-release tagged `v0.0.0`, which exists so
  that AC-6 has something to install from, and which nobody can read as a version
  of the plugin. Publishing it is AC-6a, a criterion of this issue. Deciding the
  first real version, cutting its tag and checking that its archives install is a
  separate issue this run opens.
- **`--ref` installs of a revision whose manifest names an unpublished version.**
  A person installing from `main` after this lands gets the fallback, correctly,
  because `v0.0.0` will hold the pre-release archives and any later commit still
  says `0.0.0`. Making an arbitrary revision installable without compiling is the
  first real release's business, not this one's.
- **Signing and notarisation**, out of bounds in the ticket.
- **Publishing anywhere other than GitHub releases**, out of bounds in the ticket.
- **Whether the Windows archive then runs** (#1), out of bounds in the ticket.
  This issue makes it fetchable.
- **Whether `herdr plugin install` can fetch from a private repository**
  (`docs/design.md` section 9, question 1), out of bounds in the ticket.
- **`README.md:38`, "Not yet installable."** It stays as it is. This issue does
  tag and publish a release, so the sentence is no longer literally true — but
  `v0.0.0` is a disposable prerelease that exists to prove the fetch path, marked
  not-latest precisely so that nobody installs it as a version of the plugin.
  Rewriting the sentence to describe it would advertise the test tag as a way to
  install. It becomes true to change when the first real release is cut, which is
  the separate issue this run opens.

## acceptance criteria

- **AC-1** On macOS and on Linux, on x86_64 and on arm64, the `build` entry
  fetches `herdr-voice-v<version>-<target>.tar.gz` from the release tagged
  `v<version>`, where `<version>` is `herdr-plugin.toml`'s own `version` and
  `<target>` is the triple for the running operating system and architecture, and
  unpacks the binary to `target/release/herdr-voice` with the execute bit set.
  On Windows the same holds with `x86_64-pc-windows-msvc` and
  `target/release/herdr-voice.exe`.
- **AC-2** A digest for each archive is published in the same release by
  `.github/workflows/release.yml`, and the `build` entry compares the bytes it
  fetched against it before unpacking anything.
- **AC-3** A digest that does not match fails the install with a message naming
  the archive, the expected digest and the one computed. It does not fall back to
  a source build.
- **AC-4** When no archive matches the running platform, the entry builds from
  source and prints one line giving the URL that did not answer, the tag and the
  target, and saying that either no release carries that tag or that release has
  no build for this platform. The install succeeds if the source build succeeds.

  *Corrected on 2026-09-17, from "naming which of the two it is". The planner gate
  found that nothing the script fetches can tell those two apart: both answer 404
  on the same URL. Separating them needs a release-level request to the GitHub API,
  which brings a second network dependency, its own retry and failure mode, and an
  unauthenticated limit of sixty requests an hour per address that a container or a
  runner behind a shared address can exhaust — a fifth way to fail, bought for one
  clause in one message. The criterion now asks for a message that names both
  readings instead of a distinction that cannot be made.*
- **AC-4a** That decision is taken only after a bounded number of retries with a
  gap between them, because GitHub answers 404 for some minutes after a release
  publishes. A 404 that does not survive the retries is not treated as a missing
  target.
- **AC-4b** A network failure that is not a 404 — a timeout, a name-resolution
  failure, a 5xx — stops the install with a message saying to retry. It does not
  fall back to a source build.
- **AC-3a** When the archive is fetched and the digest published for it is not —
  whatever form that digest takes, and after the same retry AC-4a requires — the
  install stops, unpacks nothing and does not fall back. The message says the
  release is missing the digest for that archive and so the bytes cannot be
  checked. Added on 2026-09-17: the planner gate found this state was reachable and
  named by no criterion, while AC-2 forbids unpacking anything unverified.
- **AC-5** When the fallback runs and `cargo` is not on the machine, the install
  fails with a message that names the missing toolchain and what to do about it,
  not a bare `command not found`.
- **AC-5a** Every message in AC-3, AC-3a, AC-4b and AC-5 reaches the person through a
  failed build entry, which means the install aborted and the plugin is not
  registered. Each of those messages therefore says what state the machine is in
  — nothing installed — and what to do next, rather than only what went wrong.
- **AC-6** A container with no Rust toolchain, no `cargo` and no rustup runs
  `herdr plugin install` against this repository and ends with an installed,
  enabled plugin whose binary runs — no compilation anywhere in the log. Recorded
  in `docs/evidence.md` with the platform, the image and the command, the way the
  existing Linux section records `scripts/linux-check.sh`.
- **AC-6a** The archives AC-6 installs are published by this run: a tag `v0.0.0`
  drives `.github/workflows/release.yml`, which produces the five archives and
  their digests, and the resulting GitHub release is marked a prerelease and not
  latest, with notes saying it exists to verify the install path and is not a
  version of the plugin. The tag matches `herdr-plugin.toml`'s `version` because
  the fetch path requires it, not because any gate checks it.
- **AC-6b** The release from AC-6a still exists when AC-6's evidence is written,
  so `docs/evidence.md` does not point at something that has been deleted.
- **AC-7** `herdr plugin link .` in a checkout still registers the plugin and
  still needs nothing but a local `cargo build --release`, exactly as
  `README.md:63` and `scripts/linux-check.sh:333` describe today.
- **AC-8** `herdr-plugin.toml:7-9` and `docs/design.md:346-349` describe what the
  manifest does, or say nothing. No sentence in the repository claims a fetch
  that does not happen.
- **AC-9** `python3 scripts/check_manifest.py`, `cargo test`,
  `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` all pass.
- **AC-10** Whatever the `build` entries end up running is covered without a live
  herdr and without the network: the platform-to-target mapping, the tag
  derivation from the manifest, the digest comparison and the fallback decision
  are each exercisable on this machine.

## Risk

The `build` entry is the one thing in this repository with no second chance. It
runs once, on a stranger's machine, before herdr registers anything, and a
failure there is an install that does not exist rather than a feature that
misbehaves. The two failure shapes are opposite: too strict and a person who
could have compiled is stopped for a missing archive; too lax and the digest
check becomes a comment, which is exactly the defect this issue is about — a
sentence describing a mechanism nobody wrote.

The second risk is the one this issue starts from. The manifest, the design
document and the comment have disagreed with the code since the comment was
written, and none of the four gates catches it: `check_manifest.py` compares the
manifest with the binary's subcommands, not with what the build entries do.
