# AC_66 — spawn errors, script fixtures and download fixture

Covers #101, #66, #62 and #48. Read against `3dd45b8` (`0.1.0-beta.5`); every
line number below was read on this branch.

## As-is

### #101 — what starting herdr reports

`src/delivery.rs:183` has `start_failure(binary, &io::Error) -> DeliveryError`.
It reads `error.kind()`: `NotFound` becomes `DeliveryError::NotFound` (the
"not on the PATH" sentence), `PermissionDenied` becomes
`DeliveryError::NotExecutable`, anything else becomes
`DeliveryError::StartFailed` carrying the operating system's own text. The
function is private and returns `DeliveryError`; its tests are
`src/delivery.rs:575-610`.

Five places still map every error from starting the program to not found:

| place | what it does |
|---|---|
| `src/setup.rs:512`, `:532`, `:549` | `Err(_) => Err(self.not_found())`, which builds `HerdrError::NotFound { binary, path }` (`src/setup.rs:492`) for `open_pane`, `check_config` and `notify` |
| `src/indicator.rs:227` | `Err(_) => Err(PaintError::NotFound { binary, path })` in `HerdrPainter::output` |
| `src/doctor.rs:112` | `Err(_) => Finding { state: Missing, detail: "cannot run {binary}; install herdr, or set HERDR_BIN_PATH to it" }` in `herdr_finding` |

`HerdrError` (`src/setup.rs:398`) and `PaintError` (`src/indicator.rs:86`) each
have two variants, `Rejected` and `NotFound`, and a `Display` that prints the
"not on the PATH this process has" sentence for `NotFound`. Neither has a
variant for a program found but not runnable, or for another operating-system
error. `src/stt/command.rs` and `src/rewrite/command.rs` already separate the
kinds, as the issue says.

Existing tests: `src/setup.rs:2284`
(`a_binary_that_cannot_be_started_is_reported_as_not_found`) and
`src/indicator.rs:1222`
(`a_herdr_that_cannot_be_started_is_not_found_and_names_the_path`) cover a
missing program only. Nothing in `src/doctor.rs` covers `herdr_finding`'s
failure arm for a program that is present but not runnable.

### #66 — scripts written and then executed

Five test modules write a shell script, `chmod` it and execute it through the
code under test, in a test binary that runs every test as a thread of one
process:

- `src/indicator.rs:1050-1058` (`fake_herdr`)
- `src/delivery.rs:436-445` (`recorder`) and `:679-689` (`a_program_that_starts_and_fails_is_still_a_rejection`, which writes its script inline)
- `src/setup.rs:2160-2183` (`herdr_cli::Recorder::new`)
- `src/bias.rs:259-271` (`scratch_script`)
- `src/bias/pane.rs:121-129` (`scratch_script`)

`src/stt/command.rs` and `src/daemon.rs` run `sh -c "<text>"` and write no
file; they are not part of the pattern. The issue says six files; five were
found by searching `src/` for `#!/` and `set_permissions`.

The cause, as established in the comments on #66: `ETXTBSY`. A test writes the
script; a sibling test in the same process forks while that write descriptor is
open; the child holds the descriptor until its own `exec`; the first test's spawn
lands in that window and fails with "Text file busy (os error 26)". Evidence
recorded there: `ubuntu-latest`, run 37275092322,
`delivery::tests::a_program_that_starts_and_fails_is_still_a_rejection`,
`StartFailed { reason: "Text file busy (os error 26)" }`. The same run's setup
test failed through the blanket arm of #101 as `NotFound`.

Measured on this machine while assessing (Darwin, Python `subprocess`): running
a script that is still open for writing succeeds; so does running it after
close. On macOS `ETXTBSY` does not occur for this, which is why the failure has
only been seen on Linux. No container runtime is installed here.

Production code spawns the program (`HerdrDeliverer::run`,
`HerdrPainter::output`, `HerdrCli`, the bias collectors). The test only writes
the script and calls the production method, so a retry placed in a test cannot
sit around the spawn itself.

### #62 and #48 — the download fixture

`serve` (`src/stt/fetch.rs:265`) binds `127.0.0.1:0`, starts a thread and
returns `(base, JoinHandle)`. The thread:

- accepts connections non-blockingly and returns, dropping the listener, when
  750 ms pass with no connection (`:274`, `:280`). The timer starts when the
  thread starts;
- reads the request head, takes the first line, and answers with the first entry
  of `files` whose suffix the line `contains` (`:303`); the request is not kept
  anywhere.

`an_unreachable_address_says_so_rather_than_hanging` (`src/stt/fetch.rs:475`)
binds `127.0.0.1:0`, reads the port and drops the listener in an inner scope,
then fetches from that port expecting `FetchError::Http`.

The six tests named in #62 fail with "Connection refused" on the address their
own `serve` returned. Port reuse after a sibling's drop, which #62 names, would
make the unreachable-address test connect to someone else's server; it would not
make a test's own live listener refuse. The 750 ms deadline would: a thread
starved of CPU past 750 ms before the client first connects returns and closes
the listener. Neither mechanism has been measured on this branch; the issue
states port reuse as "a contributing cause".

`one` (`src/stt/fetch.rs:154-157`) builds
`"{base}/{repo}/resolve/{revision}/{name}"` from `entry.revision`. The fixture
entry's revision is forty zeros (`src/stt/fetch.rs:363`). #48 records that
replacing the expression with a fetch from `main` left the suite green.

## To-be

- Starting herdr fails with a message that says the program is missing, or that
  it was found but cannot be run, or what the operating system said, according to
  the error kind, in setup, the indicator and doctor as in delivery.
- A test that writes a script and runs it cannot fail because the script is
  still open for writing somewhere in the process, and the guard is written once
  and used by every one of the five fixtures.
- The download fixture's listener stays bound as long as its test uses it, the
  unreachable-address test gets its address without freeing a contested port, and
  the fixture keeps the path it was asked for.
- A test fails when the download is pointed at anything other than the revision
  the entry pins.

## Requirements

Asked for by the issues:

1. (#101) Each of the five arms distinguishes a missing program from the other
   reasons, using #78's helper if it fits. A test per module for a missing
   program and for a program without the execute bit.
2. (#66) The cause named with its evidence; the fixture cannot lose its script;
   a test that reproduces the race, or a plain statement of why one cannot be
   written. The fix is for the class, in every module that has it.
3. (#62) The listener a test is given stays bound while the test uses it; the
   unreachable-address test gets its address another way; the six tests pass
   under the load that reproduced the failures, repeated enough times to mean
   something.
4. (#48) The test double records the path it was asked for; a test fails when the
   fetch uses anything but the pinned revision; the mutation is re-run and goes
   red.

Implied, not asked: a Windows build with `-D warnings` still compiles (the
brief's dead-code check), because the shared fixture code is unix-only.

Chosen readings of what is ambiguous:

- "Distinguishes" in #101 means three outcomes: not found, found but not
  runnable (permission denied), anything else with the system's text. That is
  #78's split, not a new one.
- For doctor, the finding's `state` stays `Missing` in all three outcomes; only
  the `detail` text changes. The issue asks for the reason to be distinguished,
  not for a new state.
- "The class" in #66 is the five modules listed under as-is. A script written
  by a test in a sixth place later is not covered by a test, only by the helper
  being the obvious way to do it.
- The retry or ordering in #66 lives in test code only. Production code reports
  the real error since #78; a retry there would hide the failure #101 exists to
  show.
- "Under load" for #62 is the load the issue describes: several concurrent
  suites plus CPU load.

## Acceptance criteria

**AC-1** In `src/setup.rs`, `HerdrCli::open_pane`, `check_config` and `notify`
return a different outcome, with different text, for each of: the program is not
found; the program exists and is not executable; another operating-system error
(its own text appears in the message). The "not on the PATH" sentence appears
only for the first.

**AC-2** In `src/indicator.rs`, `HerdrPainter::output` does the same as AC-1 for
its three public calls, and the journal line from `paint_failed_line` carries
the right sentence for each.

**AC-3** In `src/doctor.rs`, `herdr_finding` returns a finding whose `detail`
differs for the same three outcomes, whose `state` is `Missing` in all three, and
whose `detail` for the first still says to install herdr or set `HERDR_BIN_PATH`.

**AC-4** Each of `setup`, `indicator` and `doctor` has a test for a missing
program and a test for a program without the execute bit, and each test fails if
its arm is changed back to the blanket not-found.

**AC-5** `rg 'Err\(_\) =>' src/setup.rs src/indicator.rs src/doctor.rs` finds no
arm that discards the error from starting herdr.

**AC-6** The five fixtures listed under as-is get their script onto disk and
executable through one shared piece of test code. No fixture contains its own
write-and-`chmod` sequence for a script it then runs.

**AC-7** The shared code is compiled only for `cfg(all(test, unix))` (or a
narrower condition), contains no `cfg(windows)` branch that CI cannot exercise
unseen, and passes `cargo clippy --all-targets -- -D warnings` on a scratch copy
with the `cfg(unix)` gates stripped (the Windows dead-code check in the brief).

**AC-8** A test exists that holds a write handle open on a fixture script, then
asks the shared code for a script that is safe to execute, and shows the
`ETXTBSY` case being waited out and not returned. On macOS, where the error does
not occur, the test states that and still passes; on Linux it exercises the
error.

**AC-9** No change to production code is needed for #66: `git diff` of the
non-test code in `src/` for #66 is empty. (The production changes in the diff are
those of AC-1 to AC-3.)

**AC-10** `an_unreachable_address_says_so_rather_than_hanging` no longer binds
an ephemeral port and drops it. It gets an address that nothing can be listening
on without relying on a port a sibling test could be given.

**AC-11** The listener returned by `serve` stays bound until the test that
called it is finished with it, not until a quiet deadline. The server thread
still ends, so no test blocks on `join` in a failure case (the hang the comment
at `src/stt/fetch.rs:255-263` records).

**AC-12** `serve` records the request line it received, in a form the test can
read after `join`, for every request, including the ones it answers with 404.

**AC-13** A test in `src/stt/fetch.rs` asserts that each of the three files was
requested at `/<repo>/resolve/<revision>/<name>` with the revision the fixture
entry pins, and that revision is not `main`.

**AC-14** With the fetch changed to use `main` instead of `entry.revision`,
`cargo test` fails, and the failing test is the one from AC-13. The command and
its output are in `docs/evidence.md`.

**AC-15** Evidence that the flake is gone, in `docs/evidence.md` with the
platform: the affected tests (all of `indicator`, `delivery`, `setup`, `bias`
and `stt::fetch`) run in a loop under parallel load on this machine, with the
number of runs stated; and two clean `ubuntu-latest` CI runs of the `check`
workflow on the pushed branch, with both run ids. A statement that the loop on
this machine cannot show `ETXTBSY`, because macOS does not produce it, sits next
to the loop result and is the reason the CI runs are the evidence for #66.

**AC-16** The four gates in the brief pass fresh: `cargo test`, `cargo clippy
--all-targets -- -D warnings`, `cargo fmt --check`,
`python3 scripts/check_manifest.py`; so does the Windows dead-code check.

**AC-17** The pull request has one `Closes #<n>` line for each of #66, #101, #62
and #48.
