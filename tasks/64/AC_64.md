# AC_64

## as-is

`.githooks/pre-commit` runs three checks in order. The second is the private
word list (`.githooks/pre-commit:26-35`): it is wrapped in
`if [ -f "$root/.leakwords" ]; then … fi` and has no `else`. When the file is
absent the block is skipped, the third check runs, and the hook exits 0 having
printed nothing — the same output as a commit that passed all three checks.

`.leakwords` is untracked on purpose (`.gitignore:8`), so a fresh clone and a fresh
`git worktree add` both start without it. `CONTRIBUTING.md:14` tells a
contributor to copy `.leakwords.example` once per clone, but nothing in the hook
notices when that was not done. In issue #41 a worktree without the file took
eight commits through the generic rules alone.

`.leakwords.example` contains only comment lines. A `.leakwords` copied from it
unchanged is a valid, empty list: the loop skips blank lines and lines starting
with `#`, and the hook passes.

No test exercises the hook. Shell tests for other scripts live in `scripts/`
(`scripts/test-release-kind.sh`) and are run by `.github/workflows/check.yml:76-80`.

## to-be

A commit made in a checkout without `.leakwords` cannot pass unnoticed: the
hook stops it and says why and how to fix it. A commit made in a checkout with
`.leakwords` behaves exactly as today.

## requirements

From the issue's "Done when":

- R1. In a checkout without `.leakwords`, the hook fails, naming the file and
  saying how to create it from `.leakwords.example`.
- R2. In a checkout with `.leakwords`, the hook behaves exactly as it does today.
- R3. A test runs the hook both ways.

Implied, not asked for: none added.

Reading chosen where the issue is open: the issue allows either failing or
succeeding after a warning on standard error, and asks for the choice to be made
before implementation. This run makes it, in this document, and the choice is
failing (R1). The basis:

- `CLAUDE.md` names a silent no-op that looks like a pass as a defect of the same
  weight as a wrong transcript. A warning leaves the commit succeeding, so the
  commit still looks like a pass to any caller that does not read standard error:
  a script, an agent, or a person who has seen the same line on every earlier
  commit. In issue #41 that would have been eight identical warnings.
- Failing costs one command, once per clone. It also does not shut out a
  contributor who has nothing to protect: `cp .leakwords.example .leakwords`
  produces a valid empty list, which passes today and keeps passing (AC-3).
  Creating the file becomes a deliberate act instead of an omission.

## acceptance criteria

- AC-1. With `.leakwords` absent and a staged change that passes the other
  checks, `.githooks/pre-commit` exits non-zero.
- AC-2. In that case standard error names `.leakwords` and gives the command
  `cp .leakwords.example .leakwords`.
- AC-3. With `.leakwords` present and no entry matching the staged diff, the
  hook exits 0 and prints exactly what it printed before this change.
- AC-4. With `.leakwords` present and an entry matching the staged diff, the
  hook exits 1 with the same messages as before this change.
- AC-5. A script under `scripts/` runs the hook in a scratch git repository in
  both states (AC-1/AC-2 and AC-3/AC-4) and exits non-zero if any expectation
  fails. It does not touch the worktree's own `.leakwords`.
- AC-6. `.github/workflows/check.yml` runs that script.
- AC-7. `CONTRIBUTING.md` says that the hook refuses to run without
  `.leakwords`.

## Out of scope / noticed

- The issue's own out-of-bounds list stands: `.leakwords` is not committed,
  `.github/workflows/leak-gate.yml` and `.gitleaks.toml` are not changed.
- The hook does not print a confirmation when it checks `.leakwords`. AC-3
  forbids adding one: the issue requires the present-file path to behave as
  today.
- The fallback in check 1, when `gitleaks` is not installed, checks fewer
  patterns and is also silent about it (`.githooks/pre-commit:17-22`). Not part
  of this issue; `CONTRIBUTING.md:15` already documents it.
