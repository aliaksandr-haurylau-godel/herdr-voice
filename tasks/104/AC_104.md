# AC_104 — The configuration popups

One run for four issues: #104 (the whole configuration from one popup, including
the speech model and the rewrite model), #103 (the microphone popup), #46 (a model
choice leaves the engine untouched) and #49 (`write_model_key` has no tests). The
input is GitHub; none of the four issues has a comment.

References such as [E9] point to `tasks/104/AC_104_evidence.md`, where each fact is
tied to a path and line or to the command that produced it.

## As-is

**Configuration.** Every setting lives in `config.toml` and is edited by hand. It
has eight sections: `[audio]`, `[stt]`, `[rewrite]`, `[ui]`, `[delivery]`,
`[context]`, `[ptt]`, `[record]` [E1]. Values are strings, booleans, integers, one
float, and two arrays of strings (`[stt] command`, `[rewrite] command`) [E7]. A file
that cannot be read, or does not parse as the configuration, makes `config::load`
return every default without an error [E6].

**The daemon.** It reads the file once, at start, and builds from it a speech engine
that stays resident, a recorder that owns the `[audio]` values by value, and a
runtime holding the other sections [E2, E3]. The source comment gives the reason for
reading once: file access on the path that runs while somebody is speaking. Requests
the daemon answers include `ping`, which `doctor` already sends [E5]. A change to
the file therefore takes effect only after the daemon restarts, which today means
restarting herdr.

**The model chooser.** `herdr-voice model --choose` lists six candle models, reads a
number with Enter, downloads the model and writes `[stt] model` through
`write_model_key` [E9, E10]. It never writes `[stt] engine`. With the defaults
(`engine = "command"`) the configured model name is used by the `command` engine only
when the configured command uses the model, and the candle files the chooser
downloads are not what the `command` engine looks for [E11]. So a successful choice
can leave the take going to an engine that does not use the model, and the
already-configured path reports success for a state that is not used (#46).
`write_model_key` has no test; its guard parses the edited text as a generic TOML
value, not as the configuration [E9, E8]. A value of the wrong type for its key
passes that guard and makes `config::load` discard the whole file [E8a]. An existing
file that cannot be read is treated as empty and then overwritten [E9].

**The microphone.** The manifest declares the `mic` popup, and the binary answers
`not implemented yet` [E12]. The input is selected by name from `[audio] input`, once
per take, from the value the recorder was started with [E4]. Devices are listed only
inside the code that opens one [E13].

**Keys and panes.** `setup` offers three bindings, `ptt`, `dictate`, `cancel`, all of
type `plugin_action` [E16]. herdr's binding types are `shell`, `pane`, `popup` and
`plugin_action`; none opens a plugin's own declared pane [E15]. An installed plugin
opens its pane from a key by declaring an action whose command runs
`herdr plugin pane open --plugin <id> --entrypoint <pane>` [E17].

**Input in a popup.** Every interactive read in the binary is a line read that needs
Enter; nothing reads an arrow key or Esc [E14].

**The rewrite model.** `[rewrite] model` can be changed only by editing the file.
`[rewrite] url` is the complete endpoint the engine posts to, ending in
`/v1/chat/completions`, not a base address [E19]. The configured server answers
`GET /v1/models` with entries that carry `id`, `object` and `owned_by` only; an
embedding model is among them and nothing in the entry tells it from a chat model
[E20].

## To-be

- `write_model_key`'s successor edits one or more keys of the configuration file in
  place, refuses an edit whose result would not load, and is covered by tests.
- One popup opened by a key lists every section and key, marks values that are
  defaults, lets a key be changed, and says for each change whether it applies to the
  next take or needs a restart.
- The speech model and the rewrite model are chosen in that popup.
- The microphone popup (`mic`) is built and opened by a key.
- A change to `[audio] input` reaches the next take without restarting herdr or the
  daemon.
- A speech-model choice leaves a configuration that uses the model, or says why not.

## Requirements

What the four issues ask for, each with its source. Items that the issues only
imply are listed at the end and are not acceptance criteria.

- R1 (#49) Tests for the configuration writer: a good edit written; an edit that
  would not parse refused with the original intact; an unwritable location giving
  instructions; removing the parse guard turns a test red.
- R2 (#104, #103) An edit changes only the key asked for, is re-parsed before it is
  written, and never leaves an unparsable file.
- R3 (#103) The `mic` popup: a key opens it; it lists inputs by name, marks the
  configured one and says when the configured name matches nothing; it is driven by
  arrows or a number, Enter, and Esc; confirming writes `[audio] input` by name; the
  next take uses it without a restart; a take in progress is not cut off.
- R4 (#103) Esc, an empty device list and an unmatched configured name each say what
  happened and what to do next; the unimplemented-`mic` test is replaced and the
  usage text names `mic`.
- R5 (#104) The settings popup: every section and key with its current value,
  defaults marked, a key changeable in place, secrets never shown, every change
  saying "next take" or "restart".
- R6 (#104, #46) The speech model chosen from the catalogue with installed or
  would-be-downloaded shown; a successful choice leaves a configuration that uses the
  model, or refuses and names the engine and what else must change; the
  already-configured path does not report a state that will not be used; the chooser's
  `run()` is covered by tests against a temporary file with no download.
- R7 (#104) The rewrite model chosen from the list the configured endpoint serves;
  when it serves none or cannot be reached, the popup says so and lets the name be
  typed.
- R8 (#103, #104) The "re-read without a restart" question is answered once and
  recorded in `docs/decisions.md`.
- R9 (#103, #104) Established by running herdr: whether a key can bind a plugin pane,
  and what it invokes if not. The key, the popup titles and any new action id are the
  owner's to choose.
- R10 (#103, #104) `scripts/check_manifest.py` passes; both popups verified by hand on
  macOS and recorded in `docs/evidence.md`.

Implied, not asked: a way to edit array-valued keys (see reading C2); changing
`[stt] token` or `[rewrite] token` (the issue says only that they are never shown);
offering the new key from `setup` (the owner's choice, #103).

## Acceptance criteria

Each criterion is answerable yes or no. "Test" means a unit test in the repository
that runs without a microphone, a model, a download or a live herdr.

### The configuration writer (R1, R2)

- **AC-1** A test writes a good edit to a temporary configuration file and finds the
  asked key changed and every other line of the original byte-identical, including
  comments and other tables. [#104 To-be 2; #49]
- **AC-2** A test whose edit would produce a file that does not load as the
  configuration finds the file on disk byte-identical to before and an error that
  names the file and the key and value refused. [#104 To-be 2, Done 2; #49]
- **AC-3** The check in AC-2 is the one `config::load` applies: a TOML-valid value of
  the wrong type for its key (for example a string for `[ui] blink_ms`) is refused by
  a test. [#104 To-be 2: "`config::load` treats an unparsable file as absent"; E8a]
- **AC-4** Replacing the guard's condition with `false` makes at least one test fail.
  [#49 Done]
- **AC-5** A test with an unwritable location (directory that cannot be created, file
  that cannot be written) finds an error that names the file and the line to add by
  hand, a non-zero outcome, and no partial file. [#49]
- **AC-6** A test with no file and no directory finds both created, holding only the
  edited key. [#49 "the directory creation"; CLAUDE.md "an absent configuration file
  is a valid state"]
- **AC-7** A test with an existing file that cannot be read finds the edit refused
  with the reason and the file untouched, not replaced by a file holding the one key.
  [#104 To-be 2: "changes only that key"]
- **AC-8** A test that sets two keys in one edit (the speech model and its engine)
  finds either both changed or neither, and the parse check run once over the result.
  [#46 Done]
- **AC-9** A test finds that setting `model` under `[rewrite]` leaves `[stt] model`
  unchanged, and the reverse. [#104: two `model` keys exist, in `[stt]` and `[rewrite]`]

### Reaching the daemon without a restart (R8, R3)

- **AC-10** After `[audio] input` is changed through the popup, a take started
  afterwards records from the new input with no restart of herdr or of the daemon.
  Test with a fake input source, and by hand on macOS. [#103 To-be 4, Done 1]
- **AC-11** A test in which the choice is made while a take is recording finds that
  take finishing on the input it started on, not cut off. [#103 To-be 5]
- **AC-12** `docs/decisions.md` has one entry for how the daemon learns of a changed

- **AC-13** After each change the popup says whether it applies to the next take or
  needs a restart, and what restart. A test or a recorded run shows, for one key the
  popup reports as applying to the next take and one it reports as needing a restart,
  that what it says is what the daemon does. [#104 To-be 6]
- **AC-14** When no daemon is running, a change is still written, and the popup says
  the daemon is not running and the change applies when it starts. [#104 To-be 6]

## Readings chosen where the text allows two

- **C1. Arrow keys and Esc.** #103 says the popup is driven by arrows or a number,
  Enter and Esc. The binary reads only whole lines, and a terminal delivers Esc and
  arrows to a line read only after Enter [E14]. The criteria state the behaviour the
  issue words, not the technique. Reading keys without Enter needs a new dependency or
  platform-specific code, on three platforms; that cost belongs to design and is
  raised with the orchestrator.
- **C2. Array-valued keys.** #104 says "a key can be changed in place". Two keys hold
  arrays of strings [E7]. The criteria cover string, boolean and numeric keys (AC-25);
  array keys are listed (AC-23) and nothing is asserted about editing them. Reading
  "every key" to include arrays is the larger reading and is raised, not assumed.
- **C3. "Set" and "default".** A key is "set" when it appears in the file, whatever
  its value, and a "default" when it does not. The alternative, comparing the value
  with the default, would call a key that someone wrote deliberately a default.
- **C4. `[rewrite] url` is the whole endpoint.** The issue speaks of "the list the
  configured `[rewrite] url` serves". The list is at the models path of the same
  server, so the address of the list is derived from `[rewrite] url` [E19]. A url that
  does not end in the chat-completions path has no derivable list address, and then
  AC-35 applies.
- **C5. Both manners of #46.** #46 allows writing `[stt] engine` alongside the model,
  or refusing and saying which engine serves it and what else must change. AC-29 holds
  for either, and the choice is left to design.
- **C6. "Next take" for a model.** The speech engine is built once and kept resident
  [E3]. #104 Done 1 says the next take uses the models; To-be 6 lets a change be
  reported as needing a restart, and asks that the restart be named. Read together:
  after the step the popup names, the next take uses the model (AC-32, AC-38), and the
  popup's statement must be true (AC-13). Whether the daemon replaces its resident
  engine without a restart, or the popup names a daemon restart, is a design choice
  and is not fixed here. The restart that counts is the one the popup names; the issue
  describes today's only restart as restarting herdr.

## Decisions the run needs, with a recommendation

Each is given as context, problem, decision, reason.

**D1. The shape of the run.**
Context: four issues; #103 and #104 share a writer, a reload mechanism and a way to
open a popup from a key; #49 tests the writer and #46 changes the speech-model choice
that #104 reuses.
Problem: one pull request for four issues is large, and #104 needs what #103 builds.
Decision (recommended): two pull requests, the second on top of the first. First:
#103 with #49, carrying the shared writer, the reload mechanism, the `mic` popup and
the key. Second: #104 with #46, on this branch.
Reason: #49's tests are the tests of the writer #103 generalises, so the writer is
fixed and tested once; #46 is the speech-model part of #104. The first pull request
needs its own branch, which the assignment does not name.

**D2. How the daemon learns of a change.**
Context: the configuration is read once and held by several threads [E2, E3]; `ping`
shows that the daemon already answers requests [E5].
Problem: re-reading the file before every take puts a file read on the path of the
keypress, and cannot apply a speech-model change unless the resident engine is
replaced.
Decision (recommended): the popup, after a successful write, sends the daemon a
request that makes it re-read the file; the reply lists which sections took effect and
which need a restart. A file edited by hand is not picked up, as today.
Reason: one mechanism serves both popups; the reply is what lets the popup say
truthfully whether a change applies to the next take (AC-13); a recording is
untouched because the new value is applied between takes.

**D3. How a key opens a popup.**
Context: herdr has no binding type that opens a plugin's declared pane [E15]; an
installed plugin does it with an action whose command runs `herdr plugin pane open`
[E17]; the `mic` pane is declared with placement `popup`, which the command's
`--placement` list does not name [E18].
Problem: without an action there is nothing for a key to bind.
Decision (recommended): declare a manifest action per popup whose command opens the
pane, and bind the key to that action as `setup` binds the others.
Reason: it is the mechanism herdr offers and an installed plugin already uses. Not yet
established: that `pane open` honours `placement = "popup"` without `--placement`
[E18, UNVERIFIED]; it is settled in an isolated herdr session (AC-39).

## Out of scope / noticed

- `status` is also declared in the manifest and answered `not implemented yet`
  [E12]. The issues do not mention it; it is left alone.
- The rewrite server's list can include models that cannot rewrite text, such as the
  embedding model it served here, and the response does not mark them [E20]. The
  popup lists what is served.
- `[stt] model` names a whisper.cpp file for the `command` engine and a candle
  identifier for `candle` [E11]. A person whose `command` uses `whisper-cli` and who
  picks a catalogue model is asked to move to the candle engine, which the
  source comment on the default records as slower for the same model [E21]. The issue requires consistency (AC-29);
  what a person on that setup should be told is a design matter and a question for the
  owner.
- A configuration edited by hand while the daemon runs stays unread until a restart
  (D2).
- `config::load` raises `[ui] blink_ms` and `[stt] command_timeout_seconds` to a floor
  [E7]. The popup shows the value in the file; the daemon may use a larger one. Showing
  the value the daemon uses is not asked for and is left alone.
- Windows behaviour of the popups is not part of the manual verification, which the
  issues limit to macOS.
