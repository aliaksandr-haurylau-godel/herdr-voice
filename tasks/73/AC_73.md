# AC_73 — the plugin id becomes `herdr-voice`

## as-is

**The id is declared once and re-used from one constant.** `herdr-plugin.toml:1`
says `id = "haurylau.voice"`. The binary holds the same string as
`pub const PLUGIN_ID: &str = "haurylau.voice"` (`src/transport.rs:18`), and
`src/setup.rs:9` re-exports that constant rather than writing the id a second
time, with the comment "two copies of the id could drift apart".

**Four things are derived from that constant, and no fifth.** Established by
reading every use of `PLUGIN_ID`:

- the state directory — `<XDG_STATE_HOME>/herdr/plugins/<id>`, or
  `<HOME>/.local/state/herdr/plugins/<id>`, when herdr does not name one through
  `HERDR_PLUGIN_STATE_DIR` (`src/transport.rs:110-126`);
- the socket, `voice.sock` inside that directory on macOS and Linux
  (`src/transport.rs:134-139`), and on Windows the pipe name itself, which is the
  bare id (`src/transport.rs:129-132`);
- the configuration directory — `<XDG_CONFIG_HOME>/herdr/plugins/config/<id>`, or
  the same under `<HOME>/.config`, when herdr does not name one through
  `HERDR_PLUGIN_CONFIG_DIR` (`src/config.rs:250-265`);
- the command a binding names, `<id>.<action>`, built by
  `Binding::command` (`src/setup.rs:19-21`) and printed by `render`
  (`src/setup.rs:51-62`).

The sidebar token is written with `--source <id>`: `token_args` puts
`crate::transport::PLUGIN_ID` after `--source` in the argument list for
`herdr pane report-metadata` (`src/indicator.rs:128-140`).

**A test already refuses a half-done rename.**
`every_action_the_snippet_names_is_declared_in_the_manifest` reads
`herdr-plugin.toml` and asserts `manifest["id"].as_str().unwrap() == PLUGIN_ID`
(`src/setup.rs:1683`). Changing the manifest without the constant, or the
constant without the manifest, fails `cargo test`.

**The id appears literally in twenty-five more places, and the constant reaches
none of them.** Counted, not estimated: `grep -rn "haurylau\.voice"` over the
working tree, minus `target/`, minus the artifacts of earlier runs under
`tasks/`, minus `docs/evidence.md`, minus the manifest and the constant
themselves, gives twenty-five lines in four kinds:

- sixteen test assertions that spell the id out rather than interpolating
  `PLUGIN_ID` — nine in `src/setup.rs`, two in `src/transport.rs`, two in
  `src/config.rs`, two in `src/indicator.rs`, one in `tests/setup_process.rs`;
- four checks that assign it in shell or PowerShell —
  `scripts/install-check.sh:30`, `scripts/linux-check.sh:30`,
  `scripts/test-install.sh:55`, `scripts/test-install.ps1:49`;
- two documents that print it inside a command a reader is meant to type —
  `README.md:46` and `CLAUDE.md:116`;
- two module comments, `src/config.rs:6` and `src/daemon.rs:995`, and one string
  a user actually reads: when the daemon does not answer in time the client says
  "check `herdr plugin log list --plugin haurylau.voice`"
  (`src/client.rs:74-79`).

**herdr accepts an id with no dot.** Established by running, on herdr 0.9.1, with
a throwaway plugin of this run's own: a manifest declaring a dotless id linked
without complaint, `herdr plugin list` showed it, and
`herdr plugin config-dir <that id>` printed
`<config>/herdr/plugins/config/<that id>`. Two plugins already installed on the
development machine carry dotless ids of the same shape as `herdr-voice`.

**Relinking the same checkout under a changed id leaves the old registry entry
behind.** Established by running, with the same throwaway plugin: after the
manifest's id was changed in place and `herdr plugin link .` run again,
`herdr plugin list` showed only the new id — but unlinking the new id made the
old entry reappear, marked `1 warning(s)`, still pointing at that checkout. The
registry is `<config>/herdr/plugins.json`; it held both entries the whole time,
and `herdr plugin list` shows one per checkout. `herdr plugin unlink <old id>`
removes it.

**herdr creates the configuration directory at link time and never removes it.**
Both directories the throwaway plugin caused were on disk after the run, empty,
and survived the unlink.

**The configuration that would be orphaned is real, not hypothetical.**
`<config>/herdr/plugins/config/haurylau.voice/config.toml` exists on the
development machine, 940 bytes, and carries `[stt]` with `engine`, `model` and
`command`, and `[rewrite]` with `engine`, `url`, `model` and `skip_if_plain`.
Under a new id the plugin computes a different directory, finds no file there,
and runs on defaults: `config::load` treats an absent file as a valid state and
reports `Source::Defaults` (`src/config.rs:281-288`), which is the behaviour
`docs/design.md` section 7 requires and which here would be indistinguishable
from the configuration having been read.

**The state directory that would be orphaned holds 1.5 GB.**
`<state>/herdr/plugins/haurylau.voice` on the development machine contains
`models/`, `takes/` and the live `voice.sock`.

**Three bindings on the development machine name the old id.**
`<config>/herdr/config.toml` carries `command = "haurylau.voice.ptt"` at line 79,
`command = "haurylau.voice.dictate"` at line 102 and
`command = "haurylau.voice.cancel"` at line 108. A `[[keys.command]]` block whose
command names a plugin that does not exist is still a block herdr honours: the
key is taken and nothing happens when it is pressed.

**`setup` only ever appends.** `run` reads the configuration, reports each of its
own bindings as already present or as blocked by whatever holds the key, offers
the remaining blocks, and appends them after `herdr config check` approves the
candidate (`src/setup.rs:499-620`, the append itself at `src/setup.rs:404-487`).
`decide` matches a binding of its own by exact command string
(`src/setup.rs:166-175`), so a block naming `haurylau.voice.ptt` is a stranger to
it: it is not one of its own, and it does hold `ctrl+g`, so the new `ptt` binding
would be reported as blocked — "`ctrl+g` is already held by
`haurylau.voice.ptt` … bind `herdr-voice.ptt` to a key of your choosing by
hand" — and not added. Nor could it simply be appended anyway: two
`[[keys.command]]` blocks on one key are answered by herdr with
`config: issues found` and `kept keys.command[9].key, disabled
keys.command[10].key`, measured and recorded at `docs/evidence.md:1004-1008`, and
`append` refuses a candidate herdr refuses (`src/setup.rs:468-478`).

**The old daemon outlives a herdr restart.** The daemon running on the
development machine has parent process 1: it is reparented to the init process
and is not a child of the herdr server, so nothing herdr does ends it. It holds
`<state>/herdr/plugins/haurylau.voice/voice.sock`, which a binary built from the
new id never looks at.

**The tab-label sweep does not depend on the id.** It cuts from the first
occurrence of `MARKER`, the microphone glyph (`src/indicator.rs:15`,
`src/indicator.rs:73-82`), and lists every tab through `herdr tab list` without
naming a plugin (`src/indicator.rs:152-158`). A decoration left by a daemon
running under the old id is therefore swept by a daemon running under the new
one, with no change. The sidebar token needs no sweep at all: it is written with
a time to live of three renewals and is never cleared, so it lapses within 1.8
seconds at the default once nothing renews it (`docs/design.md` section 6).

## to-be

The plugin's id is `herdr-voice` everywhere a user types or reads it, and the
person who already has the plugin installed is told, in the plugin's own words,
what the rename left behind and what to do about it — rather than pressing three
keys that do nothing.

## requirements

Asked for by the issue:

- `herdr-plugin.toml` declares `id = "herdr-voice"`, and `PLUGIN_ID` agrees.
- `setup` prints and appends bindings whose commands are `herdr-voice.*`.
- The sidebar token is written with `--source herdr-voice`, and no decoration
  left under the old source survives a daemon start.
- A user who already had the plugin is told what to do, explicitly, rather than
  finding three dead keys.
- Tests cover the rendered snippet, the manifest agreement, and the migration.
- The person is told without having to ask: a user who presses a key that the
  rename made dead learns what happened where they are, not only if they think
  to run `setup`. Read out of the issue's "told what to do rather than finding
  three dead keys" together with `CLAUDE.md`'s rule on silent failure; the
  reasoning is under "why AC-11 is not a requirement invented after the fact".

Implied, and inside the bounds:

- The four scripts and the current documents that spell the id out name the new
  one, because an installation check that greps for a plugin id herdr no longer
  knows reports a healthy install as broken.
- `setup` gains one capability it does not have today: changing a
  `[[keys.command]]` block the user already has, rather than only adding blocks.
  The issue asks that `setup` append bindings naming the new id, and on a machine
  that already has the plugin an append cannot put them on their keys — the old
  blocks hold those keys. The capability is bounded to blocks whose command names
  this plugin's own previous id, and is exercised only on an explicit answer.

Not asked for, and not done: the repository's address, the binary's name, the
action and pane ids. The issue puts all three out of bounds.

## why AC-11 is not a requirement invented after the fact

The issue's **Done when** says a user who already had the plugin "is told what to
do rather than finding three dead keys". AC-6 and AC-7 place every sentence in
`setup`, which is where the person is told once they ask. Nothing tells them to
ask: they press `ctrl+g`, nothing happens, and nothing anywhere says why.

`CLAUDE.md`, under the rules for the code, already settles what that costs:
"Every user-visible failure names what to do next. 'Silent failure' is a defect
of the same weight as a wrong transcript." Three keys that do nothing and say
nothing is that failure, and an explanation a person could find by guessing which
command holds it does not make the failure not silent. AC-11 is that existing
rule applied to the way the rename produces the same failure.

## the reading chosen where the issue can be read two ways

The issue says the rename "breaks three things at once" — bindings,
configuration, and a daemon holding the old socket — and then says, under **Done
when**, only that the user "is told what to do rather than finding three dead
keys". The narrower reading is that the bindings alone must be covered. The
reading taken here is the wider one: the notice covers all three breakages the
issue itself lists, because a person who reinstates the three keys and then finds
the plugin running on defaults, with the local model gone from `[stt]`, has been
told what to do about one third of what happened. This is AC-6 and AC-7.

## acceptance criteria

- **AC-1** `herdr-plugin.toml:1` says `id = "herdr-voice"`, and
  `src/transport.rs` defines `PLUGIN_ID` as `"herdr-voice"`. `cargo test` passes,
  which includes the assertion at `src/setup.rs:1683` that the two agree.

- **AC-2** `herdr plugin link .` on a checkout of this branch registers the
  plugin as `herdr-voice`: `herdr plugin list` names `herdr-voice` and
  `herdr plugin config-dir herdr-voice` prints a path ending in `herdr-voice`.

- **AC-3** The snippet `setup` prints contains `command = "herdr-voice.ptt"`,
  `command = "herdr-voice.dictate"` and `command = "herdr-voice.cancel"`, and no
  string containing the old id. A test asserts this on the rendered snippet.

- **AC-4** The argument list for the sidebar token has `herdr-voice` after
  `--source`. A test asserts the argument list, as `src/indicator.rs:941-950`
  already does for the old value.

- **AC-5** The old id survives in exactly one place in the source: a constant
  `LEGACY_PLUGIN_ID` beside `PLUGIN_ID` in `src/transport.rs`, whose value is
  `"haurylau.voice"`. Nothing else in `src/` or `tests/` spells the old id except
  the tests that assert on the migration notice and on that constant.

- **AC-6** Run against a configuration that carries `[[keys.command]]` blocks
  naming `haurylau.voice.*`, `setup` reports each such block as this plugin's own
  predecessor — naming the key it sits on and the file it sits in — and not as an
  unrelated command holding the key. It then offers, in one `[y/N]` question, to
  rewrite those blocks so they name `herdr-voice`, and rewrites them only on `y`.
  After the rewrite the file's `[[keys.command]]` blocks carry `herdr-voice.ptt`,
  `herdr-voice.dictate` and `herdr-voice.cancel` on the keys the old blocks held,
  every other block and every other line of the file is what it was, and
  `herdr config check` answers `config: ok`. On anything but `y` the file is
  unchanged. Covered by tests over both answers, on a fixture whose blocks carry
  comments above them and inside them: the file this edits is hand-written, and
  on the machine it runs on the `ctrl+g` block is preceded by the reason that key
  was chosen. A rewrite that took a block out and put a replacement at the end of
  the file would leave that comment above whatever followed it, describing a
  binding no longer there.

- **AC-7** In the same run, `setup` also says:
  1. where the configuration file under the old id is and where the plugin now
     looks — and, if the design chooses to carry the file over, that it did;
  2. that a daemon started under the old id may still be running, and the one
     thing that ends it.

  Each is covered by a test asserting on the output.

- **AC-8** No file in the working tree names `haurylau.voice` except in four
  places: `LEGACY_PLUGIN_ID` in `src/transport.rs`, and the tests that assert on
  it or on the migration notice, both of which need the string to do their work
  (AC-5); the artifacts of earlier runs under `tasks/`; and the recorded
  measurements in `docs/evidence.md`. The last two are records of what was true
  when they were written. Checkable with `grep -rn "haurylau\.voice" .
  --exclude-dir=target --exclude-dir=tasks --exclude-dir=.git
  --exclude=evidence.md`: every line it prints must be in `src/transport.rs` or
  in a test.

- **AC-9** `cargo test`, `cargo clippy --all-targets -- -D warnings`,
  `cargo fmt --check` and `python3 scripts/check_manifest.py` all pass.

- **AC-10** A daemon started under the new id leaves no decoration from the old
  one behind: a tab whose label carries the microphone marker is stripped at
  start-up, and a token written under the old source is gone. Verified by running
  and recorded in `docs/evidence.md`.

- **AC-11** When the herdr configuration still carries at least one
  `[[keys.command]]` block naming `<legacy id>.<action>`, the daemon raises one
  notice at start — not per take, not per keypress — saying how many such keys
  there are, which keys they are, that the plugin's id changed, and that `setup`
  repairs them. When no such block is there, it says nothing. A notice that
  cannot be raised is recorded in the plugin log instead of taking the daemon
  with it, through the path `src/daemon.rs:691-699` already uses. Covered by
  tests over all three cases.

## out of scope / noticed

- **The state directory, and the 1.5 GB of models in it, is orphaned by the
  rename.** The issue names the state directory as derived from the id but does
  not list it among what breaks, and `model --choose` downloads a model again
  without loss of anything but time and bandwidth. Whether the notice in AC-7
  should also name the old state directory is a design question; it is not an
  acceptance criterion here.

- **The old registry entry stays in `plugins.json` after a relink.** Established
  above. It shows as a warning rather than as a second plugin, and
  `herdr plugin unlink haurylau.voice` removes it. Whether the AC-7 notice names
  this is for the design.

- **`docs/evidence.md` and `tasks/*` keep the old id.** They record what was
  measured and decided under it. Rewriting them would make the record disagree
  with the runs it describes.

- **The repository's address still carries the surname.** The issue puts it out
  of bounds explicitly.
