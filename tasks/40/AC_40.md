# AC_40

While a take is recording, something on screen says so. Issue #40 is the ticket.

## as-is

**Nothing in the plugin draws anything.** No code sets a sidebar token or a tab
label. The only outward calls to herdr are delivery and toasts —
`src/delivery.rs:213` `vec!["pane", "send-text", pane, text]`, `:218`
`vec!["agent", "prompt", pane, text]`, `:223`
`vec!["notification", "show", title, "--body", body]` — plus one read,
`src/bias/pane.rs:20`.

**The configuration has no keys for it.** `src/config.rs` `Ui` holds `toasts`
and nothing else, while `docs/design.md` section 7 names `blink_ms`,
`sidebar_token` and `tab_indicator`.

**herdr can draw a token on a pane, and the token can expire.**
`herdr pane report-metadata <pane_id> --source <id> --token <name>=<value>
[--clear-token <name>] [--seq <n>] [--ttl-ms <n>]`. Verified by running it on
2026-09-14: a token set with `--ttl-ms 6000` appeared in `herdr pane get` as
`tokens: {"voice": "REC 0:05"}` and was gone when the same command was run seven
seconds later. The same subcommand also offers `--title`, `--display-agent` and
`--state-label <STATUS=TEXT>`, none of which has been exercised here.

**herdr can rename a tab, read a tab's label back, and that is permanent.**
`herdr tab rename <tab_id> <label>` changes it; there is no time to live.
`herdr tab get <tab_id>` reports the current one as `label`, which is what makes
a restore that does not clobber possible at all. Verified by running both on
2026-09-14.

Three things that came out of running them, each of which the restore has to
survive:

- **A tab's `label` and its `number` are different fields**, and a label that
  looks like a number can still be one somebody typed. The tab used for this
  check reported `label = "6"` with `number = 8`.
- **An empty rename is accepted and sets the label to the empty string**, after
  which herdr shows the number. So "no label" is a value a restore may have to
  write back, not an impossible state.
- **The restore is only as good as the value read before decorating.** Both of
  the above were established by decorating a live tab and putting it back, and
  the putting back only worked because the original had been read first. That is
  this issue's own failure mode, met while establishing its mechanism.

**The daemon already knows where to draw.** The invocation context carries
`focused_pane_id`, `tab_id` and `tab_label` (`src/context.rs:11-16`), all parsed
today, and a take pins its pane when it begins — so the pane and the tab to
decorate are in hand from the first keypress.

The context's `tab_label` is **not** what the restore should use, for the reason
requirement 2 gives: it arrives only on a keypress, so it cannot see a rename
made during the seconds the pipeline runs after the key comes up, and once the
plugin has renamed the tab it reports the plugin's own decoration back. The
value to restore comes from `herdr tab get`.

**There is now something worth showing.** Since #17 a hold moves through four
states — opening, live, ending, idle — and a take then moves through bias,
recognition, rewrite and delivery. Before #17 there was one take shape and no
stages worth naming.

**And there is now a reason beyond tidiness.** A hold keeps recording for one
second after the key comes up. Measured by hand on 2026-09-14: a 15.32-second
hold produced a 16.12-second recording. For those 800-odd milliseconds a working
recording and a hung one look exactly alike, and the same take's level is
reported nowhere at all (#59).

## to-be

While a take records, the pane's row in the sidebar carries a token saying so,
with elapsed time. After the key comes up, the same place names the stage the
take is in. The tab label carries the same information for someone whose sidebar
is collapsed. When the run ends — any way at all, including the daemon being
killed — nothing decorated is left behind.

## requirements

1. **The token is renewed, not cleared.** It carries a time to live **longer**
   than the renewal interval — a small multiple of it — so that the token is
   continuously present while a take runs, and lapses within a bounded time of
   the daemon ceasing to renew it, whether it finished, failed, was killed or
   wedged. The design's "cleared on every exit path" becomes "kept alive only
   while there is something to say": the same outcome, with no path to miss and
   no clearing call to make.

   The multiple is design's, and it is a trade: larger means a token that
   outlives a dead daemon for longer, smaller means more calls to herdr per
   second of recording. It must not be so small that an ordinary scheduling
   delay makes the token flicker — a token that lapses between renewals is a
   different design, and it would pre-decide the blink question below.
2. **The tab label is restored explicitly**, because nothing expires it, and the
   value to restore is read before the label is decorated rather than taken from
   the invocation context. The context's `tab_label` arrives only on a keypress,
   and after the key comes up no request reaches the daemon for the seconds the
   pipeline runs — so it cannot see a rename made during those seconds, and once
   the plugin has renamed the tab itself the context reports the plugin's own
   decoration back to it. `herdr tab get` is what closes that: read the label
   before decorating, and before restoring read it again and compare with what
   was written. Equal means nobody touched it and the original goes back;
   different means somebody renamed it during the take and it is left alone.
3. **Both places show the same thing**, so that a collapsed sidebar loses
   nothing but the place it was shown.
4. **Elapsed time is visible while recording**, so that a stuck take is
   distinguishable from a working one.
5. **The stages after release are named**, not merged into one "working": a take
   spends seconds in recognition and seconds more in rewrite, and those are the
   waits a person wonders about.
6. **The indicator costs nothing on the keypress path.** Holding a key starts the
   client about twelve times a second and the daemon answers each repeat in under
   a microsecond (`docs/evidence.md`). Drawing must not happen per repeat, and
   must not put a `herdr` subprocess on that path.
7. **A drawing failure is not a take failure.** herdr being unavailable, slow, or
   refusing the call loses the indicator and nothing else; the take goes through.
   It is recorded once, not per frame.
8. **Both halves are switchable**, with defaults, per `docs/design.md` section 7:
   `sidebar_token` and `tab_indicator`, plus `blink_ms`.

## What this stage hands to design, undecided

**What "blink" means with a time to live.** The design says the indicator blinks.
Renewal is already periodic, so a blink is free — alternate the token's text or
drop it every other renewal. Whether it should blink at all is worth deciding
rather than inheriting: a blinking token is what the eye catches, and a steady
one with a running clock may say more.

**What the token's name and value look like.** Both are user-visible in the
sidebar, and naming is the owner's; this stage does not fix them.

**Whether the tab indicator is a prefix, a suffix or a replacement**, and what
happens to a label that is already long.

**Who draws.** The daemon owns the take and the stages; it is also what dies
unexpectedly. Design decides whether the drawing lives on the watcher thread,
on its own, or somewhere else, and what happens when a draw outlives the take it
described.

**Whether the take's level belongs here.** Issue #59 says a hold's level is
reported nowhere, and the indicator is the obvious place for it. This stage does
not require it; design may take it if it is free, and #59 stays open either way.

## acceptance criteria

- **AC-1** While a take records, the pinned pane's row carries a token naming
  that it is recording and how long it has been.
- **AC-2** The token disappears on its own within a bounded time of the daemon
  ceasing to renew it, with no clearing call made — demonstrated by killing the
  daemon mid-take and observing the token go.
- **AC-3** After the key comes up, the token names the stage: recognition,
  rewrite, delivery.
- **AC-4** The tab label carries the same information and is restored to what it
  was when the take began. A take that ends any way — success, failure,
  cancellation, a device lost — leaves the label as it found it.
- **AC-5** A tab renamed by the person during a take is not overwritten by the
  restore, including a rename made after the key came up, while the pipeline
  runs. The check is a read-back comparison, not the invocation context.
- **AC-5a** An empty original label is restored as an empty label, not skipped
  as though there were nothing to restore.
- **AC-6** No `herdr` call is made on the keypress path. The measured per-repeat
  cost stays within an order of magnitude of what `docs/evidence.md` records
  today.
- **AC-7** herdr failing, hanging or refusing the drawing call does not fail the
  take, and is recorded once per take rather than per frame.
- **AC-8** `[ui] sidebar_token`, `[ui] tab_indicator` and `[ui] blink_ms` exist
  with defaults, and either half can be turned off independently.
- **AC-9** Everything above is covered by tests that need no herdr: the drawing
  goes through a recorded call, the way delivery already does
  (`src/delivery.rs:64`), and the clock seam from #17 drives the elapsed time.
- **AC-10** Verified by hand on macOS through a live herdr pane: a held key
  shows a token and a decorated tab, the token clears itself when the daemon is
  killed mid-take, and the label comes back. Recorded in `docs/evidence.md`.

## Out of scope / noticed, not turned into a criterion

- **The level in the indicator** (#59). Named above as design's option.
- **Toasts**, which exist and are not changed.
- **The preview step and the run journal**, both off by default and unbuilt.
- **`--title`, `--display-agent` and `--state-label`**, the other three things
  `report-metadata` offers. Only tokens are needed here; the rest is a wider
  change to how a pane presents itself and belongs to whoever wants it.
- **Cancellation** (#18). `cancel` still stops nothing, so the cancellation path
  in AC-4 is exercised by a take that fails, not by one that is cancelled.

## Risk

The indicator is the first thing this plugin draws rather than writes, and the
first that must be undone. The token's time to live removes the undo for one
half; the tab label keeps it for the other, and that half is where a missed path
leaves a person with a permanently decorated tab. The design's own warning is
the thing to respect: a renamed tab that is not restored stays wrong forever.

The second risk is noise. This draws on every take, including the ones that
work, and an indicator people learn to ignore is worse than none: it costs
attention and buys nothing.
