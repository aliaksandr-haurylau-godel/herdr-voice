# AC_93 — a daemon whose herdr has gone must still answer, and doctor must be able to tell

Issue: #93. Input: GitHub issue body. Platform of the failure: macOS,
`0.1.0-beta.4`.

## As is

- herdr starts the daemon from `[[startup]]` with standard error connected to a
  pipe herdr reads. When herdr exits the daemon keeps running and keeps the
  socket; nobody reads the pipe.
- The daemon writes to standard error with `eprintln!`, which panics when the
  write fails. On a serving path the panic is in `serve_one`
  (`src/daemon.rs:1478`, `src/daemon.rs:1480`) and in `StderrJournal::write`
  (`src/daemon.rs:1097`). The connection thread dies before it writes a reply and
  the client prints `malformed header: ""` and exits 1.
- Other `eprintln!` calls reachable while serving: `src/daemon.rs:1430`,
  `src/daemon.rs:1443`, `src/daemon.rs:1452`, `src/daemon.rs:1459`, and
  `src/capture/cpal_source.rs:44` (runs when a take opens the device).
- `doctor` reports the daemon as `ok` after a bare connect
  (`src/doctor.rs:146`). The daemon returns from a connection that sent nothing
  before it writes anything (`src/daemon.rs:1475`), so the probe never reaches the
  failing write.
- The new herdr runs `[[startup]]` again, finds the socket held, and exits with
  `AlreadyRunning`; the old daemon keeps answering.

## To be

- A failed write to standard error changes nothing about what the daemon does.
- Nothing on a path reached while serving can panic because of standard error.
- `docs/design.md` states what happens to a daemon whose herdr has gone.
- `doctor` fails when the daemon it finds does not answer a real request.

## Requirements

1. **Request path survives a dead standard error.** A test runs the request path
   (`serve_one` or the function it is split into) with a journal whose writes fail
   and asserts that the reply is written and is the reply the command produces.
2. **No `eprintln!` or `println!` on a serving path.** Every write the daemon
   makes to standard error from the moment the socket is bound goes through one
   writer that discards a failed write. That includes the request line, the
   context note, accept and connection failures, thread-join failures, and the
   capture module's duplicate-device notice. A test on the writer itself uses a
   sink that always fails.
3. **The decision is written down.** `docs/design.md` says whether a daemon left
   behind by a herdr restart keeps serving or notices and exits, in the
   four-part form (context, problem, decision, why), and says what makes the new
   herdr end up with a daemon that answers.
4. **`doctor` sends a real request.** The `daemon` finding is `ok` only when a
   request sent to the daemon comes back with a reply. When it does not — no reply
   within the client bound, a reply that is not a valid frame, or an error reply —
   the finding is `missing`, `doctor` exits non-zero, and the detail says what to do
   next. The request used must not change the daemon's state (see Constraints).
5. **Verified by hand**, on macOS, recorded in `docs/evidence.md` with the
   commands and their whole output: with a daemon running, its herdr goes away, then
   an action is run. A negative result is recorded as such. The run states which of
   two methods it used: a herdr restart against an isolated herdr server, or a daemon
   started by hand with standard error on a pipe whose reader was closed.

## Constraints

- The doctor probe must not start, stop or cancel anything. `cancel` answers
  `nothing to cancel` today (`src/daemon.rs:169`) and does nothing else; if it
  ever does something, a probe that uses it would act on a person's live take. The
  design picks a request with no effect and says why.
- `src/doctor.rs` is also changed by issue #85. The edit here is limited to
  `daemon_finding` and its tests.
- The four gates in `CLAUDE.md` ("Local development") pass, and so does the Windows dead-code check: clippy with `-D warnings` on a copy of `src/` whose `cfg(unix)` items are switched off.
- Nothing from the owner's live plugin, herdr server or daemon is touched.

## Out of scope

- Reporting through `herdr plugin log list` in a new form; the journal keeps its
  lines and its text.
- Daemon-side timeouts on `Command::output()` calls.
- The pre-commit hook printing nothing for `.leakwords` (issue #64).
- The stale-environment question (whether an old daemon's `HERDR_*` variables
  still point at the new herdr) is a question for S2 to settle, and S5 to measure;
  it is not an acceptance criterion by itself.
