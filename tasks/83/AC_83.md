# AC_83

## as-is

`scripts/install.ps1` fetches the release archive and its `.sha256` sidecar,
verifies the digest with `Get-FileHash` (`:170`), and then unpacks the
archive with the native `tar` command found on `PATH`:

```powershell
tar -xzf $hvArchiveFile -C $tmp
```

`$hvArchiveFile` (`:141`) is `Join-Path $tmp $archive` — an absolute path,
built from `[System.IO.Path]::GetTempPath()` plus a fresh GUID directory
(`:130`). `$tmp` at `-C` is the same absolute temporary directory.

`scripts/test-install.ps1:77` builds its own fixture archive the same way:

```powershell
tar -C $stage -czf $fakeArchive "herdr-voice-v0.4.2-$target"
```

`$fakeArchive` (`:76`) is `Join-Path $fixture 'archive.tar.gz'` — also an
absolute path.

On a machine with a typical Git for Windows / PortableGit install, `tar` on
`PATH` resolves to the MSYS/Cygwin build shipped there
(`C:\programs\PortableGit\usr\bin\tar.exe` on the machine this issue was
filed against and this run was done on), ahead of the native bsdtar Windows
has shipped in `System32` since build 1803. Confirmed in this session with
`where tar` and `(Get-Command tar -All).Source`, under both Windows
PowerShell 5.1 and `pwsh` 7 — both resolve the MSYS build first.

MSYS tar reads a colon appearing before any slash in a filename argument as
a `[user@]host:file` remote-archive specification (the traditional GNU tar
remote-file syntax `rsh`/`ssh` builds still honor). An absolute Windows path
handed to `-f` (as `-xzf`/`-czf` do implicitly) — `C:\Users\...\archive.tar.gz`
— is therefore parsed as "connect to host `C`", which is exactly the failure
both scripts hit:

```
tar (child): Cannot connect to C: resolve failed
gzip: stdin: unexpected end of file
/usr/bin/tar: Child returned status 128
/usr/bin/tar: Error is not recoverable: exiting now
```

Two things this session confirmed empirically, both load-bearing for the
fix's shape:

- An absolute path given to `-C` does not trigger the bug — only the archive
  path bound to `-f`/`-czf`/`-xzf` does, and only when it is absolute with a
  drive-letter colon.
- A relative filename for the archive argument, with the process's working
  directory already set to the right place beforehand, does not trigger the
  bug at all — proven with both a create-with-absolute-`-C`-plus-relative-`-f`
  round trip and a full create/extract round trip, both exit 0.

The issue as filed describes a different failure at a different line —
`Get-FileHash` at `:170` being unresolved — with a two-step diagnostic
(`$PSVersionTable`, `Get-Command Get-FileHash`,
`$PSModuleAutoLoadingPreference`, `$env:PSModulePath`; then the install's own
invocation shape reproduced directly) that the issue's own text says settles
whether the fix belongs to the cmdlet-resolution branch or to something else.
Re-run in this session, on the same machine the issue was filed against
(`$PSVersionTable.PSVersion` = `5.1.26100.9444`, an exact match to the
issue's recorded value): `Get-Command Get-FileHash` resolves to
`Microsoft.PowerShell.Utility`; `$PSModuleAutoLoadingPreference` is unset
(default); `$env:PSModulePath` includes the System32 WindowsPowerShell v1.0
Modules directory; and the install's own invocation shape —
`powershell -NoProfile -ExecutionPolicy Bypass -Command "if (Get-Command
Get-FileHash -EA SilentlyContinue) {'found'} else {'NOT FOUND'}"` — printed
`found`. The issue's own text: "`found` means the cmdlet resolves under the
install's own invocation, and the cause is something else... Say so in the
issue and stop; the fix will be different." A real install
(`herdr plugin install aliaksandr-haurylau-godel/herdr-voice --yes`) was also
run twice on this machine to try to reproduce the filed failure directly:
both times `Get-FileHash` resolved and the digest verified without incident,
and both times the run instead failed at the `tar` call two lines later, with
the stderr quoted above.

## to-be

`scripts/install.ps1` unpacks the verified archive without depending on
which `tar` implementation `PATH` happens to resolve first. The archive is
extracted with the process's working directory set to the destination
directory and a bare relative filename passed to `tar`, so no absolute
Windows path with a drive-letter colon ever reaches an argument MSYS tar
parses as a remote-archive spec — regardless of whether the `tar` on `PATH`
is the native bsdtar or an MSYS/Cygwin build.

`scripts/test-install.ps1`'s own fixture-building `tar` call is fixed the
same way, so the test suite runs cleanly on a machine with a typical
Git-for-Windows/PortableGit install, which is not a rare local configuration
for a Windows contributor.

The digest verification step (`Get-FileHash` at `:170`) is unchanged — it
does not reproduce as broken on this machine, and per the issue's own stated
branching logic ("say so in the issue and stop; the fix will be different"),
building the certutil/.NET fallback the issue pre-designs is out of scope for
what this run actually reproduces.

## requirements

This run's requirements diverge from the issue's own "Done when" list,
because the issue's own diagnostic — followed exactly, on the same machine —
routes to "the fix will be different" rather than into the certutil/.NET
fallback branch. The requirements below are what the reproduced defect
actually calls for, per the scope decision already made by the repository
owner (see "Resolved before this run began," below):

1. `scripts/install.ps1` extracts the downloaded archive without a bare
   `tar -xzf <absolute-path> -C <absolute-path>` invocation reaching a
   colon-bearing absolute path as the archive argument on any Windows
   machine, regardless of which `tar` `PATH` resolves.
2. The existing `if ($LASTEXITCODE -ne 0)` check immediately after the `tar`
   call (`:181-184`) keeps working exactly as today: a real extraction
   failure is still caught and still produces the existing
   "verified but could not be unpacked" message. Nothing about restructuring
   the call may let a nonzero exit code escape unchecked.
3. `scripts/test-install.ps1`'s fixture-building `tar` call (`:77`) is fixed
   the same way, so the suite builds its own fixture without hitting the
   identical bug — verified by running the suite on this machine, which has
   the PortableGit MSYS `tar` ahead of System32's on `PATH`.
4. Everything downstream of `$fakeArchive` in `test-install.ps1` — the
   `Get-FileHash` call on it, the `Copy-Item` from it inside the `RunMain`
   stub — keeps resolving to the same real archive file; the fix does not
   break any existing assertion in the suite.
5. A test exists that would fail against the unfixed code and passes against
   the fixed code, for both scripts — proving the fix by running it, not by
   inspection alone.
6. The `sh` install path (`scripts/install.sh`, `scripts/test-install.sh`) is
   untouched — out of bounds per the issue's own "Out of bounds" section and
   unaffected by this defect, which is Windows/MSYS-`tar`-specific.
7. The four gates the issue's own "Done when" already names still pass:
   `cargo test`, `cargo clippy --all-targets -- -D warnings`,
   `cargo fmt --check`, `python3 scripts/check_manifest.py` — none of this
   issue's changes touch Rust code, but the gates are still run and recorded
   per `CLAUDE.md`'s S5 rule, and `scripts/test-install.ps1` is run under
   both PowerShell 5.1 and `pwsh` 7, per the issue's own "Done when" and per
   `CLAUDE.md`'s testing section.

## What S2 has to settle, not decided by the issue or by this AC

The issue never anticipated this defect, so nothing in it specifies an exact
mechanism — only the empirical constraints established above (absolute `-C`
is safe, absolute `-f` is not; relative `-f` with the right working directory
is safe). Left to design:

- The exact mechanism for changing directory around the `tar` call —
  `Push-Location`/`Pop-Location`, `Set-Location` with a saved-and-restored
  prior location, or `Start-Process -WorkingDirectory` — and how it composes
  with the existing `try { ... } finally { Remove-Item -Recurse -Force $tmp
  ... }` block the call already lives inside in `install.ps1`, including
  where `$LASTEXITCODE` is captured relative to any location-restoring call,
  since a `Pop-Location`/`Set-Location` between the `tar` call and reading
  `$LASTEXITCODE` is safe in PowerShell (native-command exit codes are not a
  cmdlet side effect) but the plan must say so explicitly rather than leave
  it implicit.
- Whether `test-install.ps1`'s fix keeps `$fakeArchive` as the absolute path
  for its other uses (`Get-FileHash`, the `Copy-Item` inside the `RunMain`
  stub) and only special-cases the `tar` invocation's own directory/filename
  handling, or threads a relative form through more broadly — a real design
  decision per the steer already given, not to be patched blind.
- The shape of the new failing-first test(s) for both scripts, matching each
  script's existing test-double conventions (`test-install.ps1`'s
  `Check`/`CheckContains` helpers and `RunMain` child-process pattern; no
  equivalent Rust-side test exists since neither script is Rust).

## acceptance criteria

  build ahead of the native one, `scripts/install.ps1`'s extraction step
  succeeds — the same real reproduction this run performed (a scratch
  archive, `tar -xzf` against the absolute path, exit 2) does not recur
  against the fixed script.
- **AC-2.** The existing `if ($LASTEXITCODE -ne 0) { Stop-Hv "$archive was
  verified but could not be unpacked" ... }` check (`:181-184`) still fires
  on a genuine extraction failure (e.g., a corrupt archive) after the fix —
  proven by a test that forces `tar` to fail and asserts the existing stop
  message, not just that the good-path case now succeeds.
- **AC-3.** `scripts/test-install.ps1` builds its own fixture archive
  without hitting the tar/PATH bug, verified by actually running the suite
  on this machine (PortableGit's MSYS `tar` ahead of System32's on `PATH`).
- **AC-4.** Every existing assertion in `scripts/test-install.ps1` that reads
  `$fakeArchive` or depends on its digest (`Get-FileHash $fakeArchive`, the
  `Copy-Item` inside `RunMain`'s good-path stub) continues to pass —
  the fixture-building fix does not break any pre-existing case.
- **AC-5.** A new test in `scripts/test-install.ps1` demonstrates the fix by
  failing against the pre-fix `tar -xzf $hvArchiveFile -C $tmp` shape and
  passing against the fixed shape — either by driving the real extraction

  (PortableGit's MSYS tar is genuinely on `PATH` here, so no mock is needed

- **AC-6.** `scripts/install.sh` and `scripts/test-install.sh` are not
  modified by this issue.
- **AC-7.** `cargo test`, `cargo clippy --all-targets -- -D warnings`,

  `docs/evidence.md` with the platform, per `CLAUDE.md`'s S5 rule.

## Out of scope / noticed, not turned into a criterion

- The certutil/.NET `Get-FileHash` fallback the issue's own text pre-designs.
  Explicitly conditional in the issue's text on Step 2 saying `NOT FOUND`;
  Step 2 said `found` on this machine both times it was run in this session.
  Not built here. If a machine that genuinely cannot resolve `Get-FileHash`
  is found later, that is a separate, still-open defect against the
  original issue text, not something this run's evidence can settle either
  way.
- `scripts/install.sh` / `scripts/test-install.sh`. Explicitly out of bounds
  per the issue's own "Out of bounds" section, and this defect is
  MSYS-`tar`-on-Windows-specific — the `sh` path is not affected by it.
- Changing which `tar` the script prefers (e.g., invoking
  `C:\Windows\System32\tar.exe` by full path rather than fixing the
  argument shape). Not needed: the relative-filename-plus-cwd approach works
  correctly against *either* tar implementation, verified for the MSYS one
  in this session; forcing a specific binary path would be a narrower fix
  solving less of the underlying ambiguity, and CLAUDE.md's own rule against
  branching platform differences inside the binary where they can be
  avoided argues against hand-picking one tool over the other when a
  PATH-agnostic argument shape is available instead.
- Any change to how `install.ps1` resolves or downloads the archive, or to
  the digest-verification step at `:170` — neither reproduces as broken
  here.
