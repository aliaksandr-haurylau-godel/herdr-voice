# AC_28 — outward calls get a stated bound, and a failing program's error is cut safely

Issues: #28 (outward calls have no bound) and #94 (`String::truncate` panics on a
multi-byte character). One run, one pull request closing both. Input: the GitHub
issue bodies and comments. Platform: all; the by-hand check is on macOS.

## As is

Read against `main` at `3dd45b8`, not taken from the issues.

**Outward calls with no bound.** Every one of these runs `Command::output()` (or
`.output()` on a `Command`) and waits for the process to exit:

- Delivery: `HerdrDeliverer::run` (`src/delivery.rs:220`) runs `herdr pane send-text`,
  `herdr agent prompt` and `herdr notification show`.
- Transcription: `CommandEngine::transcribe` (`src/stt/command.rs:132`).
- Rewrite: `CommandEngine::rewrite` (`src/rewrite/command.rs:96`).
- Bias: `pane::read` (`src/bias/pane.rs:64`), called from `src/bias.rs:93`.

`src/stt/http.rs:18` and `src/rewrite/http.rs:93` already bound their HTTP engines at
30 seconds; the command engines have no counterpart.

**What a wedge does.** A take reaches these calls by two paths.

- The `dictate` toggle runs the pipeline on a connection thread
  (`src/daemon.rs:1445`). The `delivering` journal line is written before the
  delivery call (`src/daemon.rs:962`) and the `delivery failed` line only after it
  returns (`src/daemon.rs:1006`). A call that never returns writes no
  `delivery failed` line, and that thread never ends.
- A push-to-talk hold runs bias, transcription, rewrite and delivery on the one
  `watch` thread that lives as long as the daemon (`src/daemon.rs:513`, `end_take`
  at `:630`). No client waits on it; a failure reaches the person through
  `report_failure`, a journal line and a toast (`src/daemon.rs:706`). A call that
  never returns keeps the hold in `Ending`, so every later `ptt` and `dictate` is
  refused with "still being transcribed" (`src/daemon.rs:283`, `:434`), and the
  `watcher.join()` at shutdown (`src/daemon.rs:1455`) waits for ever.

On the toggle path the bias read, transcription, rewrite and delivery run one after
another inside one client wait of 120 seconds.

**What the person sees.** The client waits `REPLY_TIMEOUT` of 2 seconds for every
command except `dictate`, which waits `WORKING_TIMEOUT` of 120 seconds
(`src/client.rs:17`, `:23`, `:32`). On expiry it prints "the daemon did not answer
within N seconds" (`src/client.rs:77`). So the issue's "two-minute bound" is the
`dictate` bound; a wedged call reached from any other command would be reported
after two seconds.

**The recorded transcription reasoning.** `docs/decisions.md` has the entry that the
client's bound is chosen by command name, with the reason that a bound turns a hang
into a message and is not there to cap work somebody asked for. No entry states a
policy for delivery, for the command transcriber, for the rewrite command or for the
pane read.

**The truncation panic (#94).** `stderr.truncate(STDERR_LIMIT)` with
`STDERR_LIMIT = 400` at `src/stt/command.rs:152` and `src/rewrite/command.rs:116`,
on text produced by `String::from_utf8_lossy`. `String::truncate` panics when the
length is not on a character boundary. Both lines are as the issue states. No other
`truncate` on text from outside the process exists in `src/`: the other matches are
the `truncated` fields of the bias result, a comment, and a test fixture truncating
its own byte vector (`src/stt/fetch.rs:415`).

**Since the triage.** #93 merged: the daemon's standard-error writes go through
`src/stderr.rs`. It does not touch the lines above.

## To be

- Each of the four outward calls has a stated policy: a bound, or a recorded reason
  for having none.
- The policy in the code and the policy in `docs/decisions.md` are the same.
- A bounded call that runs out of time ends its thread, and the person is told which
  program did not answer, not that the daemon did not.
- Both command engines cut a failing program's standard error on a character
  boundary and never panic.

## Requirements

What the issues ask for:

1. A stated policy per outward call, recorded in `docs/decisions.md` (#28). Delivery
   and transcription are decided deliberately, not assumed to share an answer (#28
   body, "Context"). The pane read is raised as a third call that probably belongs on
   the delivery side (#28 comment).
2. A wedged program produces a message naming what wedged, not a report that the
   daemon is unresponsive (#28 "Done when").
3. A wedge does not leave a thread behind (#28 "Goal" and "Context"), on the toggle path and on the push-to-talk path alike: on the second the stuck thread is the watcher, and the goal's "silent take" is the person left with no message.
4. Tested with a program that sleeps, without a live herdr (#28 "Done when").
5. Both truncation sites cut at a character boundary at or below the limit and never
   panic (#94).
6. A test per engine with a failing fake program whose standard error puts a
   multi-byte character across byte 400, asserting the failure is reported with the
   error text (#94).
7. No other `truncate` on text from outside the process remains in `src/` (#94).

What the issues only imply, written down so design does not discover it late:

- A bound shorter than the client's wait is the only kind that can produce a message
  naming the program. If a policy lets a call run as long as or longer than the
  client's bound for the command that reaches it, the client's report wins and the
  message is the wrong one again. This follows from requirement 2.

## Acceptance criteria

- **AC-1.** `docs/decisions.md` has one entry for each of: delivery's herdr calls,
  the external transcriber, the rewrite command, the pane read. Each states a bound
  or a reason for having none, in the four-part form `CLAUDE.md` requires for a
  decision (context, problem, decision, why).
- **AC-2.** The delivery policy and the transcription policy are different from each
  other, or the entry for one says why they are not. (#28: "the two may not deserve
  the same answer, and that is the decision this issue has to make".)
- **AC-3.** For every call whose AC-1 entry states a bound, the value in the code
  equals the value in the entry, and a test pins it.
- **AC-4.** For every bounded call, a test runs a program that sleeps past the bound,
  without herdr, and asserts the call returns within a limit of the bound plus a
  stated margin.
- **AC-5.** For every bounded call, the error the call returns names the program and
  the bound, and says what to do next (`CLAUDE.md`: "every user-visible failure names
  what to do next").
- **AC-6.** Toggle path: a delivery that times out writes the `delivery failed`
  journal line, and the reply to the client names herdr, not the daemon. A test
  asserts both.
- **AC-7.** Toggle path: a transcription or rewrite call that times out reaches the
  person as a message naming the program, not as the client's "did not answer". If
  the transcription entry states no bound, it says why, and states what the person
  sees after the client's own bound. The bounds of the calls on this path, added
  together, are shorter than the client's wait for `dictate`, or the entry says what
  the person sees when they are not.
- **AC-8.** After a timeout, the process that was run is not left running, and the
  thread that ran it returns. A test asserts the process is gone.
- **AC-9.** `src/stt/command.rs` and `src/rewrite/command.rs` cut standard error at
  a character boundary at or below 400 bytes and do not panic for any input.
- **AC-10.** For each of the two engines, a test runs a failing fake program whose
  standard error has a multi-byte character spanning byte 400, and asserts the
  returned error contains the text before the cut.
- **AC-11.** `grep -rn "\.truncate(" src` finds no call on text that came from a
  program, a file, a socket or the environment.
- **AC-12.** A new configuration key, if the policy introduces one, has a default and
  an absent configuration file stays valid (`CLAUDE.md`: "Configuration keys have
  defaults").
- **AC-13.** The four gates pass: `cargo test`, `cargo clippy --all-targets -- -D
  warnings`, `cargo fmt --check`, `python3 scripts/check_manifest.py`.
- **AC-14.** Hold path: a bounded call that times out ends `end_take`, the hold
  returns to `Idle`, a journal line and a toast name the program (`report_failure`),
  and a following `ptt` is accepted. A test asserts this through the watcher with a
  sleeping program.
- **AC-15.** Hold path: if the transcription entry states no bound, it says what the
  person sees and what happens to later `ptt` and `dictate` presses and to shutdown
  while the program has not returned.

## Chosen readings

- **The rewrite command is in scope.** #28's body names delivery and transcription,
  and its comment adds the pane read. The rewrite command is not named in either. It
  is included because the run assignment names it and #94 changes the same module;
  it is a further unbounded external program on the same thread. Remove AC-1's
  rewrite entry and the rewrite half of AC-4, AC-5 and AC-7 if that assignment was
  wrong.
- **"A policy, or a recorded reason for having none"** applies to each call, so a
  call may end with no bound. The issue's own text leans that way for transcription
  ("a person may reasonably wait minutes"). AC-7 covers that case so the person still
  gets a message naming the program.
- **"Delivery" means the three herdr subcommands named in the issue.** The same
  `herdr` binary is also run by the indicator (`src/indicator.rs:224`) and by the
  rename notice (`src/daemon.rs:1397`); neither is named, see below.
